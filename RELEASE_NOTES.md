# Release notes

## v0.5.0

**Six new profiler subcommands, and a contract that fails the build when one of them claims more than it read.** 0.4.3 was about claims that asserted more than the code delivered; this release adds new surface under the same rule, with the machinery to enforce it rather than the discipline to remember it. **Four things were deliberately not shipped** rather than shipped in a form that does not work — a Cursor adapter, three `doctor` environment tiers, a time limit on `experiment run`, and a spool-to-profile projection — and each is named below with the reason. No profile schema keys changed meaning and the schema stays `skill-architect/profile/v1`.

- **`profiler compare` subtracts two profiles, and refuses the pair it cannot trust.** Two profiles whose `capability.adapter_version` differ are **refused, not reconciled**: the difference between them may be the reader rather than the skill, and this project has shipped two consecutive releases in which the same export produced different totals. The refusal is upstream of every subtraction rather than a flag set after one, and both versions reach the report. Two differing `snapshot_hash`es, by contrast, are a **note and never a refusal** — comparing a skill before and after a change is the entire purpose, and a document claiming otherwise was corrected here.
- **`profiler experiment {design,plan,run}` schedules and executes a paired with-skill/without-skill run.** Three refusals at three times. A design may declare only what the runner actually does — `ordering: blocked`, `analysis_method: difference`, `stopping_rule: fixed`, and `$PROFILE` in each command — so the draft's `ordering: random` with a note saying it would be run blocked, which is a request the tool ignores, is refused instead. A run stamps each profile path before and after the command, so a step that exits 0 and writes nothing is refused rather than compared as this run's numbers. And each profile is read back and checked against the step's declared `harness`, `snapshot_hash` and `skill_dir`, so the plan's declaration is a promise that is kept. The command that runs the agent is still yours to supply; the plugin never launches a model or spends tokens of its own.
- **`profiler experiment run` has no time limit. There is no cap of any kind.** It shells out to the command each step declares, in a loop, and waits. A step that never terminates never terminates. A draft declared a `Budget{MaxTokens, MaxTimeMs}` that nothing read, and it was **dropped rather than shipped as a cap that does not cap** — a token cap especially cannot prevent the spend it names, because the count is only known after the step. This release does prove a portable bash-3.2-safe deadline in its own test library (`mutation_bounded` in `tests/lib/mutation-runner.sh`), and Go offers `exec.CommandContext`, but neither softens that sentence: the first is a test library and nothing in `experiment run` sources it, and the second is not called. **Impose your own time limit when you run one.**
- **A Cursor hook spool: `profiler ingest` and `profiler hooks {install,uninstall}`.** This is **capture only** — the payload is written as it arrived, so a reader written later works from files that already exist. Numbers survive exactly: the decoder uses `UseNumber()`, because decoding through a generic map puts every number through `float64` and a nanosecond epoch is about 1.7×10¹⁸, and a payload whose numbers were silently rounded on the way to disk is not recoverable by a better reader. The claim is "no field is dropped and no value is changed", with object key order and duplicate keys as the two named exceptions. `prompt`, `command`, `tool_input`, `tool_output` and their neighbours are `[REDACTED]` by default; `--strict` reduces them to their byte sizes. Installing merges into an existing `~/.cursor/hooks.json` — a re-run adds nothing and writes nothing — and uninstalling removes only our own entries.
- **None of the hook spool has been checked against a running Cursor, and its payload shapes come from documentation.** No Cursor install was reachable, so that `~/.cursor/hooks.json` is the file Cursor reads, that the 21 event names are the ones it invokes, and that a payload arrives as one JSON object carrying `hook_event_name`, `cursor_version`, `cwd` and `conversation_id` are **Cursor's documentation rather than our measurement**. If any of that is wrong, `hooks install` writes a file Cursor ignores and the spool stays empty, or lines arrive with blank envelope fields. **We cannot tell you it works against Cursor.** What is proved is what the spool does with what it is handed: a line written is a line read back, byte for byte, numbers included.
- **`AppendSpool` has no locking, and Cursor may fire hooks concurrently.** It is one write of the whole line under `O_APPEND`. POSIX guarantees the offset update is atomic and a single write of a line is not split in practice on APFS or ext4, but it is not *guaranteed* for a regular file, and a line longer than the filesystem's atomic write size could in principle interleave with another hook's. A corrupted line is skipped by the reader and counted rather than costing the file, which is why this ships as a stated limit rather than as a fix — real locking is worth doing the first time anyone observes an interleaved line.
- **`profiler analyze` summarises a spool, and describes the files rather than the session.** File, line and byte counts, the envelope fields, a census of payload keys, how many lines were unreadable, and how many envelopes were stripped. It makes no inference about tokens or tool calls, and the guard for that is the type rather than the prose: there is nowhere in the summary for a token count to go.
- **`profiler doctor` says what this machine can and cannot measure — and `hooks`, `server_api` and `enterprise` are gone.** There are **two tiers, `none` and `export`**, and a tier is only ever what a probe read from a real file. A preview of this command reported a `hooks` tier when `~/.cursor/hooks.json` carried our entry, a `server_api` tier when `CURSOR_ADMIN_API_KEY` was set, and an `enterprise` tier when `OTEL_EXPORTER_OTLP_ENDPOINT` was. **If you are upgrading from that preview you will notice they are missing, and the reason is the point of the release**: none of the three is a measurement. There is no Admin API client in this repository; an OTLP endpoint is where a harness *sends* telemetry, not a file this tool can read; and no adapter in this build reads a spool, so a registered hook is a capture waiting for a reader. The mechanism that keeps it honest is structural — the function that decides a tier takes a harness name and a path, and cannot see the home, the spool or the environment, so there is nothing available to it from which a tier could be raised. What is actually on your machine is still reported, under `observed`, with counts, and every spool observation ships with the sentence saying it yields no measurement — in the document rather than only in this file, because a report gets pasted somewhere a caveat does not travel to.
- **No Cursor, Codex or Devin adapter ships, and none ever has.** Three adapter drafts existed as unlanded work, and the audit of them is why none landed. Measured for this release by copying all three into the profiler package at head and building: they do not compile — `otelMetric`, `otelLog`, `toInt` and `parseTime` were removed by v0.4.1's OTLP rewrite and all three read them. And two of them advertise what they cannot deliver, which is the one shape the new contract exists to refuse: the Cursor draft reports `tokens` from `sqlite` for any stat-able export file and then answers that same capability with "Cursor SQLite token schema not yet verified", and the Devin draft reports `tokens` from `session_data` and returns an unknown result on every path that reaches it. There is no input for which either delivers what it advertised. The README marked all three "Planned" before this release and still does. **The Cursor work that is real does ship** — the spool, `analyze` and `doctor` — as capture infrastructure and not as an adapter, and the harness row says exactly that.
- **An adapter contract, enforced as a table that fails the build.** Three obligations, each asserted in the direction it fails: a capture names one session and refuses an empty id; a count that was not read has no key in the profile rather than a zero; and a capability a probe advertised must be `present` in the profile from the source it named, with the converse also checked, so a value the profile carries must have been advertised. The checks are a function returning violations rather than assertions calling the testing package, which is what lets the table's own ability to fail be under test. The registry the CLI resolves `--harness` through is the same list the table walks, and a scan fails the build if an adapter is constructed in the command and escapes it. A future adapter cannot ship while it over-advertises, whether or not anyone remembers this decision.
- **The Claude Code adapter reads skill activation — from the event, not the attribute.** `claude_code.skill_activated` is logged when a skill is invoked and only then, so one record is one activation and the timestamp on it is an invocation time. `skill.name` also rides along on `token.usage`, `cost.usage`, `api_request`, `api_error` and `api_refusal`, where it marks a skill active *for that request*: a skill used across five requests carries it five times, at flush and request times. Reading those as activations would report a count and a set of times the harness never recorded, so an export thick with the attribute and carrying no event reports `skill_activation: unknown` with a reason naming the event that was looked for — and the fixture for that is the negative control the extractor is tested against.
- **`skill-rewrite`'s drafter takes `-o|--output`, with a bound.** It writes anywhere you can write, **except four destinations**: an existing directory, a symbolic link, any `SKILL.md`, and anything inside `$HOME/{.claude,.cursor,.codex,.devin,.config}`. A directory makes the redirect fail on its own and report "could not open" when the truth is you named a folder. A symlink gets followed and the far end truncated, so the name and the landing place are two different places. A `SKILL.md` is the document the draft was built by reading, and written over it leaves a draft where an agent next reads a skill. And the last one is the sharp one: **an agent reads `~/.claude/skills/` as skills**, so a draft dropped in one is not a stray file but a document that may be loaded as instructions. **The decision is made after resolving the path, not from its spelling** — `$HOME/drafts/x.md` where `drafts` links into `.claude/skills` is refused, and `$HOME/.claude-notes/x.md` is accepted even though `$HOME/.claude` is a string prefix of it. A destination that cannot be resolved counts as protected and exits 3: "I could not tell where this would land" is not "go ahead". The four refusals apply to the destination `-o` names; with no `-o` the draft still goes beside the target's own `SKILL.md`, as it always did. No new exit status — a destination the script will not write to is the usage error its header already registers.
- 2649 assertions across seven shell suites pass with 0 failures under **both** bash 3.2.57 and bash 5.3.15, returning the same count under each, against 0.4.3's 2499 measured the same way. 275 top-level Go test functions and 669 subtests pass under `-race`, against 0.4.3's 93 and 452, with one test skipping by design. `go test -cover`: 97.9% for the profiler package, 94.5% for the CLI, 93.5% for the home-safety package. 64 OTLP fixtures, against 59. Eight DuckDB queries ship for reading a spool, with their column list derived from the event type so a query that falls behind the schema turns a test red. Dogfooding under `skillscore@2.0.2`: `skill-audit` 92.5 (A-), `skill-rewrite` 89.5 (B+), both validating with zero errors and zero warnings.
- **The bash 3.2 half of "green on both shells" is not in CI, and that is an accepted risk rather than an oversight.** The workflow has one job, on `ubuntu-latest`, with one bash — so **every "green on CI" claim in this release is a bash-5 claim**, and the bash 3.2 half is a local macOS step in the release checklist. This is not incidental: 0.4.3's headline defect was that bash 3.2 exempts `[[ ]]` from `errexit` while bash 5 does not, so an entire suite printed PASS for failing checks on the older of the two shells this project supports. Every suite here was therefore run locally under both. Closing the gap means a second CI job on `macos-latest`, which is new CI surface rather than a gap in what shipped, and it is deliberately not in this release.
- **What this release does not close.** The deferred ledger carries **15 rows that name 0.5.0 as their home and are marked open**, audited before 0.4.3 shipped. Re-walked here, two are closed — the composite-attribute identity defect, by 0.4.3, and the CLI coverage figure, whose 12.6% turns out to have been a measurement artifact and is 94.5% once the test binary is built with `-cover` — and **the remaining 13 are open, and this release closes none of them.** They are: per-finding `jq` re-invocation in both `--json` writers; `isMonotonic` unread; a data point's `flags` unread; a `--json` exit 3 with no payload on three caller-error paths; schema v1 having no channel for a refused series; the whole-export slurp; a truncated final line costing the whole capture; a rejected tool call being indistinguishable from a failed one; the not-a-count reason's upper bound being a hair generous; the Devin, Codex and Cursor install rows being unverified; cumulative temporality never having been seen on real output; the tool attribute names being taken from documentation rather than observed; and `CaptureOpts.APIKey` being read by nothing. Four deferral markers in the documents that read "0.5.0" have been re-pointed, because this release *is* 0.5.0 and closes none of them: `probe` still has no documented exit contract, there is still no bundled receiver subcommand, and a `present` result still has no field in which to say what it did not count.
- **Three profile keys this release adds are written by nothing that ships.** `error_type`, `count` and `id` on a tool call exist in the type surface for sources that report them, and the Claude Code adapter sets none of the three — so a rejected tool call and a failed one are still both `success: false` with no classification between them. They are optional and absent, and the contract forbids advertising them, so no profile claims otherwise: the channel landed and the distinction did not. `attribution` is `unknown` on every profile this release can produce, because Claude Code's telemetry carries no output-to-skill mapping at all, and `estimated_context_tokens` is produced by no shipped adapter.
- **The skill-activation read rests on documentation as well.** The `skill.name` attribute is labelled `[DOCS]` in the fixture provenance file — from Anthropic's monitoring reference, not from an observed capture — and every activation fixture here is constructed. The same is true of `tool_name`, `success` and `decision`. The envelope, the timestamp encodings and the scope names are `[OBSERVED]`; the attribute names and values are not.
- **An experiment result embeds the whole normalized design, including both commands.** A stored result must say what it ran, so a secret spelled literally into a command travels with the document. Read a result before you publish it. Relatedly, `doctor` exits 0 whatever it finds — "nothing here measures anything" is the answer for most machines today, so a script asking "can this machine measure?" has to parse the JSON.
- **The skill metadata versions are unchanged, and whether they move is your decision rather than something to do quietly.** `skill-audit` declares `0.2.0` and `skill-rewrite` declares `0.1.0`, while the five plugin manifests go to `0.5.0`. **The skill versions are independent of the plugin version by design** — nothing asserts a relationship between them and nothing here adds one. It is more conspicuous than it was: this release changed `skill-rewrite`'s documented interface by adding a flag to it, and that skill still declares `0.1.0`.
- **A past change recorded late: `skill-audit`'s quality score fell from 94 (A) to 92.5 (A-) in 0.4.3, and the 0.4.3 notes do not say so.** Measured here under one pinned `skillscore@2.0.2` across three trees, so the drop is content rather than a tool version: v0.4.1 scores 94, v0.4.3 scores 92.5, and head scores 92.5. The category is `clarity`, 9/10 down to 8/10, on a synonym-pair warning against a `SKILL.md` that release rewrote. 0.5.0 does not touch that skill and does not change the number. The released notes are left as written; this is the record.
- **No spool-to-profile projection ships, and that was a choice.** A draft of one set `tool_calls` to `present` from `hooks` on the strength of guessed field names — a capability claim **in the data rather than in the prose**, which no documented limit can reach, because a stored profile is subtracted by `compare`, aggregated by `experiment` and read months later by callers who never see the source. What landed instead is the read that is true whether or not the guesses are right, which is also what `analyze` is built on.
- **Also deferred:** the shell containment primitive now exists three times — in the install suite, in the profiler's home-safety package, and in the drafter. They are not copies of one library and cannot be, one being a test suite, one a Go package and one a shipped script that may depend only on its sibling skill, but they are three implementations of one decision and the drift is real: the first shell version written from the Go one was weaker than its source. And `draft-rewrite.sh` can still exit 7 from a failing `rm` in its EXIT trap, outside the `{0, 1, 3}` its header states, unchanged from 0.4.3 and recorded there in full.

## v0.4.3

**Every claim in this repository is now answerable to something that runs.** Nine clusters, one release. No new features, and no profile schema keys changed. The subject throughout is claims that asserted more than the code delivered — starting with the suites, which on the older of the two shells this project supports could not report a failure at all.

- **A profile reports the session it names, and nothing else — so the numbers change for the same export.** The adapter required a session id, stamped it on the output, and filtered nothing. Both documented capture routes append to one file by design, so a profile covered every session in it. Against the repository's own two-session fixture, 0.4.2 reports 49200 input tokens and three tool calls for *either* session; 0.4.3 reports 48000 and two for one, 1200 and one for the other. A session not in the file at all came back `present` with the same confident 49200 and is now `unknown`, with a reason naming how many records do not carry the asserted id. **A stored 0.4.2 profile beside a fresh 0.4.3 one is not a regression; it is the fix**, and `capability.adapter_version` moving to 0.4.3 is what tells the two apart. The mechanism: a provenance applied once on the read path before any extractor runs, so an extractor cannot be handed the whole export by accident. A record contributes only if it carries the asserted `session.id` and its instrumentation scope is not another product's — an exclusion rather than an allowlist, because a scope is optional in OTLP and a collector may drop it, and refusing those would trade a wrong number for no number. `probe` stays unscoped and says so.
- **`check-frontmatter.sh` now requires `jq`, and `check-quality.sh` gained requirements too.** This is a new hard dependency on a path that previously worked without one. Measured by masking each tool out of PATH in turn: at 0.4.2 `check-frontmatter.sh` refused for exactly one absent tool, `skill-validator`; it now refuses for five — `awk`, `dirname`, `grep`, `jq`, `skill-validator` — and it has no `--json` mode, so text mode is where the change lands. `check-quality.sh` refused only for `skillscore` and now refuses for `dirname`, `jq` and `skillscore`. The trade is the right one and it is stated in each script's header: reading *what* a source answered needs the predicate that proves a payload readable, and that predicate is jq. Branching on an exit status alone is what let a `skill-validator` exiting 0 while printing non-JSON produce `frontmatter OK`. The full ten-tool set is in the README's Prerequisites, compared against the scripts in both directions by the suite.
- **A failing check can report FAIL.** `assert` took a *value*, so 16 of the layout suite's 17 shell `assert` call sites wrote the real check as a bare `[[ ]]` on the preceding line and handed in the literal `true` — and 7 of the walk suite's did the same, the 23 `tests/test_harness.sh` now holds. bash 3.2 does not apply `errexit` to `[[ ]]`, so on bash 3.2 a failing check printed PASS. With a shipped reference file deleted, the 0.4.2 tree printed `PASS: skill-audit best-practices reference exists` and never printed a `FAIL:` line or reached its summary. `assert` runs a command now, which removes the shape rather than patching the call sites. The suite also runs from any working directory — run from `/` under bash 3.2 it used to print `PASS: .devin-plugin/plugin.json exists` and then die trying to open that file — and an abort before the summary is loud instead of silent.
- **A missing tool cannot produce a pass, and over the ten tools these skills require, no script leaks a status outside its own contract.** Those ten are every external the scripts invoke but for `rm`, which the drafter's cleanup calls and the census does not list — which is exactly why the exit 7 below is a limit this release ships rather than a contradiction of this line — and `bash`, which cannot be missing while a bash script runs. At 0.4.2, masking `grep` from `check-paths.sh` gave **exit 0** with `grep: command not found` as its only output; masking `wc` from `check-structure.sh`, or `awk` from `check-paths.sh` or `audit-report.sh`, gave **127**; masking `grep` from `check-structure.sh` gave **2**, the status reserved for a policy failure. All of them are exit 3 naming the tool now. The guard's contract is "the tool is present **and** answered something this file proved it could read", not "a name resolved", an external's status is read where it is called, exit contracts derive from each script's own header, and `check-quality.sh` and `draft-rewrite.sh` are inside the shared guard for the first time. `sed` and `tr` were deleted rather than guarded — each did one thing the shell does itself, and neither's status was read.
- **A markdown horizontal rule no longer switches path checking off.** Four body-extraction implementations are one primitive now. Two fixtures differing by a `---` above the references section, and otherwise only in their frontmatter `name` and the line in which each names the other, used to disagree: `check-paths.sh` exited 0 on the one with the rule and 1 on the one without. Both are 1. A skill whose body is a single prose line no longer reports a pass either.
- **The rule-ID census counts what a script can emit, not what it spells.** An ID handed to the guard, one `require_tool` raises on a script's behalf, and one relayed from a child all reach a `--json` consumer leaving no literal behind, and the census credited those scripts with none of them. The registry side had the mirror defect, matching a fixed list of the prefixes already in use. Both sides read a rule-shaped token now, with transitive, cycle-guarded relay attribution, so one unregistered ID fails every script that can carry it.
- **The PATH-masking farm masks one binary and shadows none.** It copied link targets verbatim, so a relative PATH entry became a broken link, and its dedupe test was false for broken links, so the dangling name stayed in front of every working binary behind it. A test that then died at 127 looked like a test of the script, when it was a test that never reached one.
- **The documented update route converges on a second run.** It copied into an existing destination and nested a second copy of a skill inside itself, and it left the destination empty when a copy failed part-way. The install and update rows now carry the status of each route as executed in this release, with the ones that were wrong against the vendors' own CLIs corrected and a hedge written from vendor documentation replaced by what running them showed.
- **`skill-rewrite` is brought up to `skill-audit`'s conventions, and its documentation describes its own script.** Every documented invocation is anchored on a root the document defines — a bare `scripts/draft-rewrite.sh` resolved only from a working directory the document never named, and the evaluation matrix path resolved against neither skill. The drafter refuses a `-a` report that is not there instead of auditing afresh and reporting "No audit report provided"; it has an exit contract; a missing option value names the option rather than printing `$2: unbound variable`; and the temporary audit it made for itself no longer outlives the run or gets written into the draft as the draft's provenance. The SKILL.md now states its seven required tools — `awk`, `cat`, `grep`, `jq`, `mktemp`, `skill-validator`, `wc` — and the sibling `skill-audit` directory it cannot work without, and describes the draft the script actually writes rather than one with preserved frontmatter, five templates and a per-dimension checklist — none of which it produces.
- **Both skills declare the compatibility they have.** `POSIX shell (bash 3.2+ or zsh), git.` was wrong three ways in both files: every bundled script is bash throughout, nothing works under zsh, and no script runs `git`. It is `bash 3.2+.` now. The machinery holding that claim read one file, which is why the identical sentence next door went unheld for two releases; it walks a derived denominator over the shipped skills now, so a skill with no witness fails.
- **CI pins `skillscore@2.0.2` and runs a suite list it cannot fall behind.** It was installed unpinned, while `skill-validator` was pinned on the step above — and the F02 suite composes its assertions over `skillscore --json`, so a new major version from the registry breaks the suite with no change in this repository behind it. The suite glob, the workflow and the README are held to one list, and the rewrite suite is committed executable — CI invokes suites by bare path, so it had been dying at exit 126 before a single assertion ran.
- 93 Go test functions and 452 subtests pass under `-race`, against 0.4.2's 66 and 230. The shell suites are at **2499** across seven, against 0.4.2's 850 across four, and every suite returns the same count under bash 3.2.57 and bash 5.3.15. 59 OTLP fixtures, against 55.
- **Two claims in the v0.4.2 notes were false when written, and are corrected rather than rewritten.** "No `skill-audit` script tells you a skill passed when it could not check" and "across every fixture, script, mode and masked tool, nothing exits outside `{0, 1, 2, 3}`" were both true of the three tools that release's suites actually masked — `jq`, `skill-validator`, `skillscore` — and false of the sets the sentences name; the measurements above are what they look like on that tree. They divide: the exit 0 and the exit 2 falsify the first, both being verdicts a missing tool could not compute, and the three exits of 127 falsify the second on their own, 2 being inside the set that sentence names. v0.4.1's "`jq` has no guard" stopped being true at 0.4.2 and is further from true here. The released notes are left as written; this is the correction.
- **Three limitations ship with this release, stated because the release is about not overstating.** A durability clause in the install suite's prose is false: only the destination is length-bounded, and the path-word pass is quadratic over every word, taking 0.9s on a 100,000-character non-destination word and 3.6s on 200,000 while accepting the block. `draft-rewrite.sh`'s EXIT trap removes its temporary audit with an `rm` that is the last command of an AND-list, so a failing `rm` replaces the script's exit status with the tool's — reproduced at **exit 7** on both shells, outside the `{0, 1, 3}` its header states, with nothing naming `rm`. And the second of those arrived in the very round that closed its own class: the cluster whose subject is that every script reads its externals' statuses is the one that wrote that trap.
- **Deferred, with reasons.** The skill metadata versions are unchanged — `skill-audit` at 0.2.0, `skill-rewrite` at 0.1.0 — and whether they move is an open decision for you rather than something to do quietly. And the bash 3.2 half of the suites is not in CI, which runs one Linux job with one bash, so a bash-3.2-only failure would pass CI. That is the exact asymmetry the `assert`-shape defect lived in, and it is why every suite here was run locally under both shells.

## v0.4.2

**Cumulative token counts are right, and no audit script reports a verdict it could not compute.** Two fixes, one release. No new features, and no profile schema keys changed.

- **A cumulative export's totals change, in the direction of being correct.** Three defects in one merge each read as "fewer tokens than the session spent". A capture spanning several resources or scopes merged their series and let one running total replace another; a counter that restarted inside the capture discarded everything before the restart; and a flush reporting less than an earlier one on the same run took that run down with it. A profile written by 0.4.2 and one written by 0.4.1 from the same cumulative export will disagree. Delta temporality — Claude Code's default — is unaffected throughout, and `capability.adapter_version` moves to 0.4.2, which is what tells the two profiles apart.
- **A time series is what OTel says it is.** The resource it came from, the instrumentation scope that recorded it, the metric's name, and the data point's whole attribute set. The adapter keyed on the attributes alone, so two resources reporting cumulative 100 and 200 gave 200 rather than 300 — the same pair under delta gave 300 all along, which is how it hid.
- **`startTimeUnixNano` says which run of a counter a point is from, and it is now read.** The points sharing a start are one run and the run holds the greatest running total any of them reported; a point carrying a different start is a counter that restarted, and its run sits beside the earlier one instead of replacing it, so 100 followed by a restart reaching 20 is 120 and not 20. A start time of `0` is a start time that is absent — OTLP uses the protobuf JSON mapping, in which an explicit zero and an omitted field are the same message.
- **`timeUnixNano` is no longer read by the merge at all.** These are counters, so their values carry their own order and a flush reporting less than an earlier one on the same run is a capture contradicting itself, not tokens given back. Ordering by the timestamp cost real tokens: a run reporting 900 at t1001 and then 500 at t1002 came back as 500 at v0.4.1, and comes back as 900 here. The apparatus is deleted rather than repaired, because the obvious repair — keep the ordering and let each run hold its latest point — would let supplying the field that says which run a point is from make the profile report *fewer* tokens than omitting it, which is the opposite of what more information should do.
- **A point that cannot say which run it is from joins the run it is cheapest to have come from.** It came from some run — one that named itself, or one nothing else in the capture observed — so it is neither a run of its own nor free. The series holds the least total its runs can account for: the runs added, plus whatever that point reported over and above the largest of them. Runs of 100 and 20 beside an unplaceable 500 give 520, not the 500 that drops a run which named itself and not the 620 that invents a third. One export flush that omits one field no longer reports a session at twice its size.
- **A series carrying both delta and cumulative points is refused rather than resolved.** They are opposite instructions, so every way of resolving the mix invents a number the export does not contain. The refusal is counted per series and named in the reason; the well-formed series beside it still count. What a `present` result cannot yet say is that a series was refused — schema v1 has no field for it, and that is tracked for 0.5.0.
- **No `skill-audit` script tells you a skill passed when it could not check.** With `jq` absent, `check-structure.sh --json` returned `{"findings": [], "passed": true}` at exit 0 and `check-paths.sh --json` died at exit 127 with no payload at all. With `skill-validator` absent, `check-frontmatter.sh` printed `frontmatter OK`. All three now exit 3 and name the missing tool on stderr, and the two `--json` writers carry a `passed: false` payload on stdout with it — `check-frontmatter.sh` has no `--json` mode, so for it the stderr line is the whole report. `--json` requires `jq` unconditionally; text mode is unchanged.
- **A child result a parent does not recognise is an execution error, not a pass.** `check-structure.sh` read `check-paths.sh`'s 127 as success, and read an unparseable payload as "no findings". Both parents now enumerate their child's documented statuses and treat anything else as an execution error, and `passed` is derived from the computed verdict in one place instead of being hard-coded on the zero-findings branch.
- **The report composer proves a source's shape before reading a verdict out of it.** `audit-report.sh` captured its guarded child with `2>&1`, so a failing payload never parsed and the composed report said `{"passed": true, "total_findings": 0}`. And a source emitting `0`, `[1,2]`, `true` or a two-document stream took `jq` down with no report at all. One guard now owns "exactly one document", each source claims only the shape it is actually read as, and a source yielding nothing readable is named in `policy_error` with `summary.passed` false.
- **A broken guard file is an execution error, not a policy failure.** A malformed `verdict-guard.sh` exited 2 — the status reserved for "policy failure" — from every script. Each script now checks the load on both sides and exits 3. Across every fixture, script, mode and masked tool, nothing exits outside `{0, 1, 2, 3}`.
- **The JSON encoder no longer depends on your locale.** It escaped through a character class that under a UTF-8 locale matched bytes with negative ordinals, corrupting them into a sixteen-hex-digit escape — including the valid C1 controls, which JSON asks no one to escape. The decision is the ordinal now, so the same bytes come out under `C` and under UTF-8.
- **`DEP001`, `DEP002` and `PATH` are registered rule IDs.** They are in the skill's rule-ID enumeration, in every emitting script's header, and in the README. `scripts/lib/` was flattened, which clears the `deep nesting detected` warning the skill had been carrying, and the layout suite now asserts both shipped skills validate with zero errors *and* zero warnings.
- 66 profiler test functions and 230 subtests pass under `-race`, against 0.4.1's 58 and 179. The shell suites are at 850, against 0.4.1's 134, and were run under both `LC_ALL=C` and a UTF-8 locale. 55 OTLP fixtures, against 39.
- **The two known limits named in v0.4.1 are fixed here, and that note needs two corrections.** Its heading said "both 0.4.2" and its body said "fixed together in 0.5.0" — one of those was always wrong, and 0.4.2 is the right one. And "Both are described in the README and the spec" is no longer true: fixing them deleted the paragraph that described them. The v0.4.1 note is left as written; this is the correction.

## v0.4.1

**Makes 0.4.0's promises true.** One family of profiler bugs — signals reported available on structural evidence rather than on a value actually read — and documentation corrected to match the code. No new features.

- **The adapter reads the telemetry Claude Code actually emits.** It parsed an envelope nothing has ever produced, so a real OTel export came back all-`unknown` and only a hand-written file came back with numbers. It now parses OTLP/JSON — one `ExportMetricsServiceRequest` or `ExportLogsServiceRequest` per JSON object, one per line or concatenated — with the real attribute names, delta and cumulative temporality, and the spec's number-or-string integers. Two consequences worth knowing before you compare a 0.4.0 profile with a 0.4.1 one: a tool call's `success` now says whether the tool ran and succeeded rather than whether it was permitted, and the reasoning token count is gone, because Claude Code has no reasoning token type. Claude Code has no file exporter of its own, so the README now has a "Capturing an OTel export" section with two ways to produce the file.
- **A signal is `present` only when a value was read.** `probe` scanned the export for structure while `capture` extracted values from it, and the two predicates disagreed in both directions: a partial export lost the signals it did carry, while a token metric with an unreadable type or value produced `present` with all-zero counts. There is now one predicate per signal, used by both, and the capability report is derived from what was actually read.
- **A broken export says so.** An export file you supplied that cannot be read or parsed is `error` naming the failure, not "OTel export not configured". Session timing spans the earliest API request to the latest, so an out-of-order export can no longer report negative elapsed time.
- **`capture --export-file` fails instead of ignoring you.** No shipped adapter reads that flag; it used to accept the path and return an all-unknown profile.
- **Install prerequisites are documented.** `skill-validator`, `skillscore`, and `jq`, with what breaks without each.
- **`skill-rewrite` needs `skill-audit` beside it.** Its `draft-rewrite.sh` resolves the audit scripts at `../skill-audit`; copying it alone quietly produces a draft with no audit in it. Now said out loud in the README.
- **The documented install command works.** Neither `claude plugins install Okja-Engineering/skill-architect` nor `claude plugins install .` could: `install` resolves a plugin name against configured marketplaces. This release ships `.claude-plugin/marketplace.json` and documents `claude plugin marketplace add` followed by `claude plugin install skill-architect@skill-architect`, verified live against a local clone. The same commands pointed at the GitHub remote work once this release is on `main`, which is where `marketplace add` looks for the manifest.
- **Three delivered-but-undocumented profiler features are now in the README**: the `version` subcommand and the `--export-file` flag, both from 0.4.0 (the flag is reserved for a future session-export adapter), and per-signal probe detection, which landed after 0.4.0 and was rewritten here.
- **A number that is not a token count no longer becomes one.** A data point's value was carried through an out-of-range float-to-integer conversion, which Go leaves to the machine: the same export read as `input: 9223372036854775807` on arm64 and `input: -9223372036854775808` on amd64. Negative values, `NaN` and infinity were all assimilated too. None of them reaches a profile now, and the reason names the point — in one of two clauses, because they are two different defects. Which of the two you get turns on how the leaf *read*, not on how large the number is. A leaf that *decoded as a finite number* whose rounded value is negative or 2⁶³ or beyond *is not a count* and is refused. A leaf that never decoded as a finite number at all — `NaN`, infinity, or a literal too big for its own reader — says nothing, so the next leaf is read; only when neither leaf yields a number is the point reported as carrying no readable value. So `{"asInt":"9223372036854775808"}` lands in the second clause, not the first: 2⁶³ is finite and numeric, but the integer reader refused it outright.
- **Two token series that differ only by an attribute the adapter does not interpret stay two series.** They used to merge, so a session's tokens were reported as a fraction of themselves.
- **A count the export said nothing about is absent from the profile, not zero.** A cache-only export reported `input: 0, output: 0` beside its real numbers. A count read as zero still reports zero. No profile keys changed names.
- **`capture` exits 2 when it read nothing and something failed.** It exited 0 for a missing or unreadable `--otel-file`, so a script wrapping it filed the all-unknown profile as a success. The profile is still printed.
- **A capture is read to its end, or it is an error.** A stray `}` or `]` after a batch — what a doubled write or a half-unwrapped JSON array leaves behind — used to end the read silently: the batches before it came back `present`, and any batch after it was dropped without a word. That is a part of a capture reported as the whole of it, which a profile cannot show you. Such a file is now `error`, naming the batch and the byte, with nothing from earlier batches used. Blank lines and trailing whitespace after the last batch are still a clean end of file.
- **Two known limits, both 0.4.2.** Under cumulative temporality — not Claude Code's default, which is delta — token counts can undercount two ways: a capture that aggregates several resources merges their series, because resource and scope identity are not part of the series key, and a counter that resets inside one capture discards the run before the reset, because `startTimeUnixNano` is not read. Both are described in the README and the spec, and both are fixed together in 0.5.0.
- **A capture identifies you, and the README says which fields.** The capture recipe no longer sets `OTEL_LOG_TOOL_DETAILS=1`: the adapter reads nothing it adds, and it widens the export.
- **The Devin, Codex and Cursor install rows are marked unverified.** Only the Claude Code route was run against a clean install.
- **The spec now describes the code.** The `MetricResult[T any]` generic never existed; the acceptance criteria described the probe one commit out of date; the fallback reason named env vars the adapter never reads and claimed every metric carries it.
- **The `skill_activation` reason no longer says Claude Code emits no skill activation event.** It does: `claude_code.skill_activated` is logged whenever a skill is invoked, through the Skill tool or a `/` command, and carries `skill.name`, `invocation_trigger`, `skill.source` and `skill.kind`. The reason printed in every Claude Code profile now says what is actually true — this adapter does not read that telemetry yet — and names `claude_code.skill_activated` as the source it will read in 0.5.0. `skill_activation` is still `unknown` with capability `none`; only the justification changed.
- **"Snapshot-pinned" was an overstatement.** `--snapshot` is a label you supply and the profiler records verbatim. It does not hash or verify the skill directory.
- Module path corrected to `github.com/Okja-Engineering/skill-architect/profiler`; CI takes its Go version from `profiler/go.mod` instead of a stale pin four minors behind. The profiler adapter version moves to 0.4.1, since a profile's contents changed.
- 58 test functions pass — 53 in the profiler package, 5 in the CLI — and 179 subtests, under `-race`. The shell suites are at 134: 0.4.0's 131 plus three more — the two new marketplace-manifest assertions and the adapter-version one. CI now runs `gofmt -l`, `go vet` and `go test -race` rather than `go test` alone.
- v0.3.1's note that `skill-audit` scores 92.5 (A-) was true of the 0.3.1 commit. It has been **94 (A)** since 3e2efd8, and still is; `skill-rewrite` is unchanged at 89.5 (B+).
