# Release notes

## v0.5.0

**Six new profiler subcommands, and a contract that fails the build when one of them claims more than it read.** 0.4.3 was about claims that asserted more than the code delivered; this release adds new surface under the same rule, with the machinery to enforce it rather than the discipline to remember it. **Four things were deliberately not shipped** rather than shipped in a form that does not work — the three unlanded harness adapters (Cursor, Codex *and* Devin, not one), three `doctor` environment tiers, a time limit on `experiment run`, and a spool-to-profile projection — and each is named below with the reason. No profile schema key changed meaning and the schema stays `skill-architect/profile/v1`. One key's **value domain widened**, which the schema rule's own wording makes worth stating: see the upgrade bullet below.

- **`profiler compare` subtracts two profiles, and refuses the pair it cannot trust.** Two profiles whose `capability.adapter_version` differ are **refused, not reconciled**: the difference between them may be the reader rather than the skill, and this project has shipped two consecutive releases in which the same export produced different totals. The refusal is upstream of every subtraction rather than a flag set after one, and both versions reach the report. Two differing `snapshot_hash`es, by contrast, are a **note and never a refusal** — comparing a skill before and after a change is the entire purpose, and a document claiming otherwise was corrected here.
- **Upgrading: every profile you captured with 0.4.x is refused by this release's headline command, and you should know that before you reach for it.** `capability.adapter_version` moves to **0.5.0**, and `compare` refuses any pair whose versions differ. Driven: a stored 0.4.3 profile beside a fresh 0.5.0 one exits **2**, with the refusal naming both versions and every metric marked `comparable: false` upstream of any subtraction. That is the refusal working — the reader did change — but it means a stored profile library does not compare against anything captured with this release, and re-capturing is the only way through. 0.4.3 made exactly this disclosure for its own bump ("A stored 0.4.2 profile beside a fresh 0.4.3 one is not a regression; it is the fix"), and this note exists because the two halves of the same fact landed in different bullets here and neither joined them. **The other upgrade consequence is a value, not a key**: `skill_activation` can now come back `error`, where v0.4.3 documented `{present, unknown}` as its complete domain and said in the code that no export could fail it. An export that is supplied and cannot be read now yields `error` for it, alongside `tokens`, `tool_calls` and `timing`. No key changed meaning and nothing was removed, so a v1 reader that skips what it does not know is still right; a v1 reader that *switched* on those two values is now wrong about one case. The schema stays `v1` in this release — flagged here rather than decided quietly, because the changelog's own rule for bumping the schema is "v2 is required when a v1 reader would be wrong", and this is the nearest thing in the release to that case.
- **`profiler experiment {design,plan,run}` schedules and executes a paired with-skill/without-skill run.** It refuses at **four** points, and the design check is one table of rules rather than a list short enough to quote. A design may declare only what the runner actually does — `ordering: blocked`, `analysis_method: difference`, `stopping_rule: fixed`, `$PROFILE` in each command, every identifying field non-empty, and **both conditions naming the same harness**, because two harnesses measure with different meters and a difference between them is not a difference in the skill — so the draft's `ordering: random` with a note saying it would be run blocked, which is a request the tool ignores, is refused instead. A **plan document** handed to `run --plan` is refused for having no runs, a step with no command, a step with no profile path, or two steps writing the same path. A **run** stamps each profile path before and after the command, so a step that exits 0 and writes nothing is refused rather than compared as this run's numbers. And each profile is **read back** and checked against the step's declared `harness`, `snapshot_hash` and `skill_dir`, so the plan's declaration is a promise that is kept. The command that runs the agent is still yours to supply; the plugin never launches a model or spends tokens of its own.
- **`profiler experiment run` has no time limit. There is no cap of any kind.** It shells out to the command each step declares, in a loop, and waits. A step that never terminates never terminates. A draft declared a `Budget{MaxTokens, MaxTimeMs}` that nothing read, and it was **dropped rather than shipped as a cap that does not cap** — a token cap especially cannot prevent the spend it names, because the count is only known after the step. This release does prove a portable bash-3.2-safe deadline in its own test library (`mutation_bounded` in `tests/lib/mutation-runner.sh`), and Go offers `exec.CommandContext`, but neither softens that sentence: the first is a test library and nothing in `experiment run` sources it, and the second is not called. **Impose your own time limit when you run one.**
- **A Cursor hook spool: `profiler ingest` and `profiler hooks {install,uninstall}`.** This is **capture only** — the payload is written as it arrived, so a reader written later works from files that already exist. Numbers survive exactly: the decoder uses `UseNumber()`, because decoding through a generic map puts every number through `float64` and a nanosecond epoch is about 1.8×10¹⁸ (the fixtures carry `1789332594304000000`), well past the 9.007×10¹⁵ a float64 holds exactly, and a payload whose numbers were silently rounded on the way to disk is not recoverable by a better reader. The claim is "no field is dropped and no value is changed", and it has **three** exceptions, all three deliberate: object key order, a duplicate key, and **credential redaction, which is always on**. **Read the next bullet for what redaction does and does not cover — the first two releases of this note had it backwards.** Installing merges into an existing `~/.cursor/hooks.json` — a re-run adds nothing and writes nothing, byte for byte — registers the 21 events Cursor documents, and writes the `"version": 1` Cursor's schema marks required. Uninstalling removes only our own entries.
- **What redaction does, and what it does not.** Two different sets, and conflating them is how an earlier draft of this note claimed a privacy property the code does not have. **Credential-shaped fields are `[REDACTED]` in both modes**: a name whose normalized form is `auth`, `authorization`, `credential` or `credentials`, or ends in `token`, `secret`, `password`, `passwd`, `apikey`, `privatekey`, `accesskey` or `sessionkey`; and credential-shaped *substrings* inside a string — a bearer token, an `sk-`, `AKIA` or `ghp_` key, a PEM header — are replaced in place so the text around them survives. **`prompt`, `command`, `tool_input`, `tool_output` and their ten neighbours are written verbatim by default**, because on this tool they are the data. `--strict` is what reduces them, to `{"_stripped_bytes": N}` where N is the JSON-encoded size, and the line records `strict: true`. Two things follow that you should know before registering this on a shared machine: **`hooks install` does not register `--strict` and there is no environment variable for it**, so metadata-only mode is reachable only by hand-writing `hooks install --command '<path>/profiler ingest --strict --spool-dir <dir> || true'`; and **`--strict` does not remove identity** — Cursor documents `user_email` on every hook payload, it matches neither set, and it is written to disk in both modes. A spool file is a plain file that outlives the session, `0600` in a `0700` directory. Read one before you share it.
- **No line in this repository was produced by a running Cursor, and we cannot tell you it works against Cursor.** Cursor is not installed on the machine this was written and verified on. What changed for this release is that the documentary half was checked against Cursor's own current published hooks reference rather than left as a note: **the file location and the 21 event names are confirmed field for field** — `~/.cursor/hooks.json` is the User-scope location, there is no 22nd event, and the set `hooks install` registers is exactly the documented set — and the **`"version": 1`** that reference marks required is now written, which an earlier build of this command omitted. Two things are worse than the note said. **`cwd` is not a universal payload field**: Cursor documents it on `preToolUse`, `postToolUse` and `beforeShellExecution` only, and the field it puts on every payload for workspace location is `workspace_roots`, which this build does not promote — so a `cwd` promoted from a payload that carries none is blank, which is the documented fallback happening for a reason we had wrong. And **the tool-call hook payload shapes are unverified against any live emitter**: `preToolUse` and `postToolUse` were registered and never fired, because a nested `claude -p` could not authenticate on this machine. What *was* exercised live is the lifecycle half and the whole read-back path — a real hook emitter (Claude Code, not Cursor) invoking `ingest` per event, then `analyze` and `doctor` over the lines it wrote, with every count checked against the raw file. What is proved about the spool itself is what it does with what it is handed: a line written is a line read back with every field and every numeric literal intact, subject to the three exceptions named above.
- **`AppendSpool` takes no lock, and it was measured under concurrency rather than reasoned about.** Concurrent invocation is the normal case and not an edge one — Cursor's reference lists Tab hooks (`beforeTabFileRead`, `afterTabFileEdit`) as a class separate from its agent hooks — so this was driven: **40 concurrent `ingest` processes** appending to one daily file at 100 B and at 200 KB, and **16 at 8 MB**, producing a **128,003,312-byte** file. Every round wrote exactly as many lines as there were writers, **every line parsed**, and in the 8 MB round all sixteen lines had exactly **one** distinct length (8,000,206 bytes), so not one was split or interleaved. That holds structurally rather than by luck: each record is a **single `write(2)` under `O_APPEND`**, newline included in the same buffer, and each call opens its own descriptor. The residual risk is named rather than implied: **`O_APPEND` atomicity is not guaranteed on a network filesystem**, so a spool under an NFS or SMB home is outside what was measured and was **not tested** — no network mount was available. A hook killed mid-write still leaves a truncated last line, which the reader skips and counts as unreadable rather than losing the file.
- **`profiler analyze` summarises a spool, and describes the files rather than the session.** Sixteen fields: file, line and byte counts, the envelope fields by day and by event, a census of payload keys, how many lines were unreadable, and how many envelopes were stripped. It makes no inference about tokens or tool calls, and the guard for that is the type rather than the prose: there is nowhere in the summary for a token count to go. **One of the sixteen needs reading before you paste a summary anywhere.** `payload_key_values` is a census of payload key *values*, not only key names: it quotes the value of any key that is neither a content field nor numeric, up to 64 characters, and it is **unbounded in cardinality** — so every absolute working directory a capture saw, every conversation id, and any field not on the redaction list appear in it verbatim. Content fields are counted and never quoted, and numbers are counted and never tallied. Same rule as the experiment result below: read it before you publish it.
- **`profiler doctor` says what this machine can and cannot measure — and `hooks`, `server_api` and `enterprise` are gone.** There are **two tiers, `none` and `export`**, and a tier is only ever what a probe read from a real file. A preview of this command reported a `hooks` tier when `~/.cursor/hooks.json` carried our entry, a `server_api` tier when `CURSOR_ADMIN_API_KEY` was set, and an `enterprise` tier when `OTEL_EXPORTER_OTLP_ENDPOINT` was. **If you are upgrading from that preview you will notice they are missing, and the reason is the point of the release**: none of the three is a measurement. There is no Admin API client in this repository; an OTLP endpoint is where a harness *sends* telemetry, not a file this tool can read; and no adapter in this build reads a spool, so a registered hook is a capture waiting for a reader. The mechanism that keeps it honest is structural — the function that decides a tier takes a harness name and a path, and cannot see the home, the spool or the environment, so there is nothing available to it from which a tier could be raised. What is actually on your machine is still reported, under `observed`, with counts, and every spool observation ships with the sentence saying it yields no measurement — in the document rather than only in this file, because a report gets pasted somewhere a caveat does not travel to.
- **No Cursor, Codex or Devin adapter ships, and none ever has.** Three adapter drafts existed as unlanded work, and the audit of them is why none landed. **The measurement, re-run per file rather than on all three at once, because the first pass hit Go's `too many errors` cap and generalised past it:** copying each draft alone into the profiler package at head and running `go build ./...`, **`cursor.go` and `codex.go` do not compile and `devin.go` compiles cleanly**. Both of the two read `otelMetric`, `otelLog`, `toInt` and `parseTime`, which v0.4.1's OTLP rewrite removed (all four declared at `541af3e`, none at `v0.4.1`); `cursor.go` additionally reads a fifth undefined name, `getBool`, which that rewrite does not explain because it was never declared in this repository at all. `devin.go` reads none of the five. **The reason none of the three lands is the second finding, not the first**, and it is the one shape the new contract exists to refuse: two of them advertise what they cannot deliver. The Cursor draft reports `tokens` from `sqlite` whenever nothing else supplied tokens and the `--export-file` it was given can be `stat`ed, then answers that same capability with "Cursor SQLite token schema not yet verified"; the Devin draft reports `tokens` from `session_data` and never returns a count on any path — `unknown` on two of them and `error` on three. There is no input for which either delivers what it advertised. The `file:line` citations in the changelog resolve against **`0a83615`**, currently on `origin/wip/0.5.0-profiler`; no such file exists at this release's head, which is the point. The README marked all three "Planned" before this release and still does. **The Cursor work that is real does ship** — the spool, `analyze` and `doctor` — as capture infrastructure and not as an adapter, and the harness row says exactly that.
- **An adapter contract, enforced as a table that fails the build.** Three obligations, each asserted in the direction it fails: a capture names one session and refuses an empty id; a count that was not read has no key in the profile rather than a zero; and a capability a probe advertised must be `present` in the profile from the source it named, with the converse also checked, so a value the profile carries must have been advertised. The checks are a function returning violations rather than assertions calling the testing package, which is what lets the table's own ability to fail be under test. The registry the CLI resolves `--harness` through is the same list the table walks, and a scan fails the build if an adapter is constructed in the command and escapes it. A future adapter cannot ship while it over-advertises, whether or not anyone remembers this decision.
- **The Claude Code adapter reads skill activation — from the event, not the attribute.** `claude_code.skill_activated` is logged when a skill is invoked and only then, so one record is one activation and the timestamp on it is an invocation time. `skill.name` also rides along on `token.usage`, `cost.usage`, `api_request`, `api_error` and `api_refusal`, where it marks a skill active *for that request*: a skill used across five requests carries it five times, at flush and request times. Reading those as activations would report a count and a set of times the harness never recorded, so an export thick with the attribute and carrying no event reports `skill_activation: unknown` with a reason naming the event that was looked for — and the fixture for that is the negative control the extractor is tested against. **One environment variable decides whether the signal can name your skill, and the README used to tell you to leave it off.** Measured on Claude Code 2.1.221 over two live captures identical but for that one variable: with `OTEL_LOG_TOOL_DETAILS` unset, `claude_code.skill_activated` carries `skill.name: "custom_skill"` for a user-authored skill and the profile reports `custom_skill`; with it set, both carry the real name. The count and the times survive either way; the identity does not. **Set it when you are capturing a profile of a skill you wrote** — which is every skill this project exists to author — and read the README's note on what else it widens before you do. `README.md:315` said this adapter reads nothing that flag adds; it reads `skill.name`, and that sentence is corrected in this release.
- **`skill-rewrite`'s drafter takes `-o|--output`, with a bound.** It writes anywhere you can write, **except four destinations**: an existing directory, a symbolic link, any `SKILL.md`, and anything inside `$HOME/{.claude,.cursor,.codex,.devin,.config,.agents}` — **six** roots, `.agents` among them because this README documents `~/.agents/skills/` as a skills directory for both Codex and Cursor, and the refusal list is now compared against that table as well as against the skill's own. A directory makes the redirect fail on its own and report "could not open" when the truth is you named a folder. A symlink gets followed and the far end truncated, so the name and the landing place are two different places. A `SKILL.md` is the document the draft was built by reading, and written over it leaves a draft where an agent next reads a skill. And the last one is the sharp one: **an agent reads `~/.claude/skills/` as skills**, so a draft dropped in one is not a stray file but a document that may be loaded as instructions. **The decision is made after resolving the path, not from its spelling** — `$HOME/drafts/x.md` where `drafts` links into `.claude/skills` is refused, and `$HOME/.claude-notes/x.md` is accepted even though `$HOME/.claude` is a string prefix of it. A destination that cannot be resolved counts as protected and exits 3: "I could not tell where this would land" is not "go ahead". Within the bound it is an ordinary redirect — **`-o` overwrites an existing file and is idempotent**, so it can re-run over its own output the way the default destination always has. The four refusals apply to the destination `-o` names; with no `-o` the draft still goes beside the target's own `SKILL.md`, as it always did — **including when `-o` is given an empty string**, which falls through to that default rather than refusing, so a script running `-o "$DEST"` with `$DEST` unset writes into the target skill's own directory, the outcome `-o` exists to avoid. No new exit status: a destination the script refuses is the `1` its header already registers, and one it cannot resolve is the `3` it already registers for an execution error.
- 2741 assertions across seven shell suites pass with 0 failures under **both** bash 3.2.57 and bash 5.3.15, returning the same count and the same per-suite split under each, against 0.4.3's 2499 measured the same way from the tag. 285 top-level Go test functions — 284 passing and one skipping by design, `TestHomeBarrierChild`, whose body a parent test runs in a child process — and 696 subtests pass under `-race`, against 0.4.3's 93 and 452. `go test -cover`: 97.9% for the profiler package, 94.7% for the CLI, 97.0% for the home-safety package. 64 OTLP fixtures, against 59. Eight DuckDB queries ship for reading a spool, with their column list derived from the event type so a query that falls behind the schema turns a test red — **they need `duckdb` installed, which is not one of the ten tools the skills require, and no test or CI step runs them**: all eight were run by hand against a real spool on DuckDB v1.5.5 and all eight returned rows. Dogfooding under `skillscore@2.0.2`: `skill-audit` 92.5 (A-), `skill-rewrite` 89.5 (B+), both validating with zero errors and zero warnings.
- **The bash 3.2 half of "green on both shells" is not in CI, and that is an accepted risk rather than an oversight.** The workflow has one job, on `ubuntu-latest`, with one bash — so **every "green on CI" claim in this release is a bash-5 claim**, and the bash 3.2 half is a local macOS step in the release checklist. This is not incidental: 0.4.3's headline defect was that bash 3.2 exempts `[[ ]]` from `errexit` while bash 5 does not, so an entire suite printed PASS for failing checks on the older of the two shells this project supports. Every suite here was therefore run locally under both. Closing the gap means a second CI job on `macos-latest`, which is new CI surface rather than a gap in what shipped, and it is deliberately not in this release.
- **What `compare` refuses is narrower than it reads, and two new exit statuses are scriptable.** `adapter_version` is the *only* identity mismatch that refuses. A differing **`harness`**, a differing **`snapshot_hash`** and a differing **`skill_dir`** are each a **note**, exit 0, with the subtraction carried out — driven on all three. `snapshot_hash` is a note on purpose, because comparing a skill before and after a change is the whole point; the other two are a decision with a shelf life, and reading "the refusal is the reason it can be trusted" as protection from subtracting two different meters would be reading it too generously. On statuses: **`compare` and `experiment run` both exit 2** when they ran and there was nothing comparable to subtract — a status neither this file nor the changelog previously named, in a release that spends a sentence on *not* adding one to `draft-rewrite.sh`. `1` stays usage-or-step error and `0` stays "it compared something". One more limit in the same area, named by the slice that built it: **`experiment run`'s freshness stamp is `(exists, size, modTime)`**, so it catches a step that writes nothing, and a step that re-touches or rewrites a byte-identical profile from an earlier run passes it — and that earlier run's numbers are then reported as this run's.
- **What `hooks uninstall` leaves behind, and a limit the changelog carried while this file did not.** On a home with no `.cursor` directory at all, install-then-uninstall leaves three things where there were none: the `.cursor` directory, a `hooks.json` containing `{"hooks": {}, "version": 1}`, and a timestamped backup still carrying our absolute binary path in all 21 entries. The leftover file is **schema-valid** — it carries the `version` Cursor requires, which is new in this release — so it will not break a hook config you add by hand later, but it is not the machine as found and the reasoning `hooks_install.go` applies to an empty event registration ("a trace of us in a file we are meant to have left as we found it") applies one level up and is not applied there. And the backup suffix is second-resolution, so **two runs inside one second collide**: install then uninstall in the same second leaves one backup, and it holds the post-install state rather than the file you started with, so the original is not recoverable from it. The changelog said three runs; it is two, driven.
- **What this release does not close.** The deferred ledger carries **15 rows that name 0.5.0 as their home and are marked open**, audited before 0.4.3 shipped. Re-walked here, two are closed — the composite-attribute identity defect, by 0.4.3, and the CLI coverage figure, whose 12.6% turns out to have been a measurement artifact and is 94.7% once the test binary is built with `-cover` — and **the remaining 13 are open, and this release closes none of them.** They are: per-finding `jq` re-invocation in both `--json` writers; `isMonotonic` unread; a data point's `flags` unread; a `--json` exit 3 with no payload on three caller-error paths; schema v1 having no channel for a refused series; the whole-export slurp; a truncated final line costing the whole capture; a rejected tool call being indistinguishable from a failed one; the not-a-count reason's upper bound being a hair generous; the **Devin and Cursor** install rows being unverified; cumulative temporality never having been seen on real output; the tool attribute names being taken from documentation rather than observed; and `CaptureOpts.APIKey` being read by nothing. **Two corrections to that row list, both narrowing a claim this release inherited.** The install row is **Devin and Cursor, not Codex**: the ledger row says all three and has said so since 0.4.1, but `README.md`'s own Codex row records that route as verified against `codex-cli 0.153.4` with `CODEX_HOME` pointed at a scratch directory, and it has recorded that since 0.4.3. The row's narrative was wrong about Codex when it was written and this release stops republishing it. And `tool_name`, `success` and `decision` **have now been observed** on a real Claude Code 2.1.221 export — `"Read"`, `"true"` and `"accept"`, each as a `stringValue`, which is what the fixtures assume — so that row is narrower than it reads; what remains documentary is the activation attribute set and cumulative temporality.
- **Every deferral marker that read "0.5.0" is gone from the tree, and a check now holds that rather than a count.** The previous rounds of this repaired a list somebody wrote down, and each round found another instance somewhere the last round's reader did not look — so the number is no longer published. `tests/lib/forward-promise-check.sh` reads **every tracked file** (`git ls-files`, 162 of them at this release, and it reports the file count so a caller can compare it against the tree) and fails the build on a line that *assigns* work to the release being cut, while leaving a line that records history — "0.5.0 did not add one" — alone. The two release documents are scoped so that only the section for the release being cut is in play, because 0.4.3's section saying what 0.4.3 deferred is legitimately history. What those markers were waiting for is still waiting: `probe` has no documented exit contract, there is no bundled receiver subcommand, `--otel-file` is still the only input, and a `present` result still has no field in which to say what it did not count. The one that did close is skill activation, which this release reads.
- **Every profile key this release adds is written by nothing that ships. All nine of them.** Set-diffing the profile's `json:` tags against `v0.4.3` gives exactly `error_type`, `count` and `id` on a tool call; `category`, `detail`, `operation_name` and `confidence` on an attribution; and `estimated_context_tokens` with its `total`. The only place a shipped capture builds a tool-call entry sets `name`, `timestamp` and `success` and nothing else, so a rejected tool call and a failed one are still both `success: false` with no classification between them; no shipped code constructs an attribution at all, which is why `attribution` is `unknown` on every profile this release can produce — Claude Code's telemetry carries no output-to-skill mapping; and no shipped adapter produces an estimate. They are optional and absent, and the adapter contract forbids advertising a key nothing wrote, so no profile claims otherwise: the channel landed and the distinction did not. Earlier drafts of this note said three, and then eight in a different bullet. It is the whole set, which is why this sentence now names them all rather than counting them. **One key is not optional and not absent**, and it is in the capability report rather than the profile body: the report went from five keys to six, because `estimated_context_tokens` is set to `none` unconditionally and so is present on every probe and inside every stored capture. It is a signal that is always reported as unavailable, not a value nobody wrote.
- **The activation fixtures' provenance is weaker than the disclosure that covers them, and the disclosure points at the wrong attribute.** `profiler/testdata/otlp/README.md` labels `skill.name` `[DOCS]` — and `skill.name` is precisely the attribute both documents say was **rejected** as the source. What shipped keys on the *event*, `claude_code.skill_activated`, and neither that event name nor `invocation_trigger`, `skill.source` or `skill.kind` appears in either labelled paragraph; five new activation fixtures landed and the provenance ledger was not extended for the identifier the whole new signal turns on. Both labelled paragraphs are byte-identical to v0.4.3. Checked against Anthropic's monitoring reference, three fixture attribute *values* are outside the documented sets: the reference gives `invocation_trigger` as `"user-slash"`, `"claude-proactive"` or `"nested-skill"` and the fixtures use `slash_command` and `skill_tool`; it gives `skill.kind` as `"workflow"` when the skill is a workflow skill and **absent otherwise**, and two fixtures carry `"skill"`; and `skill.source` is documented as `"bundled"`, `"userSettings"`, `"projectSettings"` or `"plugin"`, where one fixture carries `"user"`. **None of it changes a number** — the adapter reads `skill.name` and passes `invocation_trigger` through as an opaque string, and reads neither `skill.source` nor `skill.kind` — but the fixtures assert an emitter shape the vendor does not document, and rewriting fixture values is not something to do during a release gate, so it is named here and left for the maintainer. The one attribute triple this release *can* report as observed rather than documentary is `tool_name`, `success` and `decision`, measured on a live 2.1.221 export. The envelope, the timestamp encodings and the scope names remain `[OBSERVED]`.
- **An experiment result embeds the whole normalized design, including both commands.** A stored result must say what it ran, so a secret spelled literally into a command travels with the document. Read a result before you publish it. Relatedly, `doctor` exits 0 whatever it finds — "nothing here measures anything" is the answer for most machines today, so a script asking "can this machine measure?" has to parse the JSON.
- **The skill metadata versions are unchanged, and whether they move is your decision rather than something to do quietly.** `skill-audit` declares `0.2.0` and `skill-rewrite` declares `0.1.0`, while the five plugin manifests go to `0.5.0`. **The skill versions are independent of the plugin version by design** — nothing asserts a relationship between them and nothing here adds one. It is more conspicuous than it was: this release changed `skill-rewrite`'s documented interface by adding a flag to it, and that skill still declares `0.1.0`.
- **A past change recorded late: `skill-audit`'s quality score fell from 94 (A) to 92.5 (A-) in 0.4.3, and the 0.4.3 notes do not say so.** Measured here under one pinned `skillscore@2.0.2` across three trees, so the drop is content rather than a tool version: v0.4.1 scores 94, v0.4.3 scores 92.5, and head scores 92.5. ## v0.4.2

**Cumulative token counts are right, and no audit script reports a verdict it could not compute.** Two fixes, one release. No new features, and no profile schema keys changed.

- **A cumulative export's totals change, in the direction of being correct.** Three defects in one merge each read as "fewer tokens than the session spent". A capture spanning several resources or scopes merged their series and let one running total replace another; a counter that restarted inside the capture discarded everything before the restart; and a flush reporting less than an earlier one on the same run took that run down with it. A profile written by 0.4.2 and one written by 0.4.1 from the same cumulative export will disagree. Delta temporality — Claude Code's default — is unaffected throughout, and `capability.adapter_version` moves to 0.4.2, which is what tells the two profiles apart.
- **A time series is what OTel says it is.** The resource it came from, the instrumentation scope that recorded it, the metric's name, and the data point's whole attribute set. The adapter keyed on the attributes alone, so two resources reporting cumulative 100 and 200 gave 200 rather than 300 — the same pair under delta gave 300 all along, which is how it hid.
- **`startTimeUnixNano` says which run of a counter a point is from, and it is now read.** The points sharing a start are one run and the run holds the greatest running total any of them reported; a point carrying a different start is a counter that restarted, and its run sits beside the earlier one instead of replacing it, so 100 followed by a restart reaching 20 is 120 and not 20. A start time of `0` is a start time that is absent — OTLP uses the protobuf JSON mapping, in which an explicit zero and an omitted field are the same message.
- **`timeUnixNano` is no longer read by the merge at all.** These are counters, so their values carry their own order and a flush reporting less than an earlier one on the same run is a capture contradicting itself, not tokens given back. Ordering by the timestamp cost real tokens: a run reporting 900 at t1001 and then 500 at t1002 came back as 500 at v0.4.1, and comes back as 900 here. The apparatus is deleted rather than repaired, because the obvious repair — keep the ordering and let each run hold its latest point — would let supplying the field that says which run a point is from make the profile report *fewer* tokens than omitting it, which is the opposite of what more information should do.
- **A point that cannot say which run it is from joins the run it is cheapest to have come from.** It came from some run — one that named itself, or one nothing else in the capture observed — so it is neither a run of its own nor free. The series holds the least total its runs can account for: the runs added, plus whatever that point reported over and above the largest of them. Runs of 100 and 20 beside an unplaceable 500 give 520, not the 500 that drops a run which named itself and not the 620 that invents a third. One export flush that omits one field no longer reports a session at twice its size.
- **A series carrying both delta and cumulative points is refused rather than resolved.** They are opposite instructions, so every way of resolving the mix invents a number the export does not contain. The refusal is counted per series and named in the reason; the well-formed series beside it still count. What a `present` result cannot yet say is that a series was refused — schema v1 has no field for it, and that is tracked for 0.5.0.
- **No `skill-audit` script tells you a skill passed when it could not check.** With `jq` absent, `check-structure.sh --json` returned `{"findings": [], "passed": true}` at exit 0 and `check-paths.sh --json` died at exit 127 with no payload at all. With `skill-validator` absent, `check-frontmatter.sh` printed `frontmatter OK`. All three now exit 3 and name the missing tool on stderr, and the two `--json` writers carry a `passed: false` payload on stdout with it — `check-frontmatter.sh` has no `--json` mode, so for it the stderr line is the whole report. `--json` requires `jq` unconditionally; text mode is unchanged.
- **A child result a parent does not recognise is an execution error, not a pass.** `check-structure.sh` read `check-paths.sh`'s 127 as success, and read an unparseable payload as "no findings". Both parents now enumerate their child's documented statuses and treat anything else as an execution error, and `passed` is derived from the computed verdict in one place instead of being hard-coded on the zero-findings branch.
- **The report composer proves a source's shape before reading a verdict out of it.** `audit-report.sh` captured its guarded child with `2>&1`, so a failing payload never parsed and the composed report said `{"passed": true, "total_findings": 0}`. And a source emitting `0`, `[1,2]`, `true` or a two-document stream took `jq` down with no report at all. One guard now owns "exactly one document", each source claims only the shape it is actually read as, and a source yielding nothing readable is named in `policy_error` with `summary.passed` false.
- **A broken guard file is an execution error, not a policy failure.** A malformed `verdict-guard.sh` exited 2 — the status reserved for "policy failure" — from every script. Each script now checks the load on both sides and exits 3. Across every fixture, script, mode and masked tool, nothing exits outside `{0, 1, 2, 3}`.
- **The JSON encoder no longer depends on your locale.** It escaped through a character class that under a UTF-8 locale matched bytes with negative ordinals, corrupting them into a sixteen-hex-digit escape — including the valid C1 controls, which JSON asks no one to escape. The decision is the ordinal now, so the same bytes come out under `C` and under UTF-8.
- **`DEP001`, `DEP002` and `PATH` are registered rule IDs.** They are in the skill's rule-ID enumeration, in every emitting script's header, and in the README. `scripts/lib/` was flattened, which clears the `deep nesting detected` warning the skill had been carrying, and the layout suite now asserts both shipped skills validate with zero errors *and* zero warnings.
- 66 profiler test functions and 230 subtests pass under `-race`, against 0.4.1's 58 and 179. The shell suites are at 850, against 0.4.1's 134, and were run under both `LC_ALL=C` and a UTF-8 locale. 55 OTLP fixtures, against 39.
- **The two known limits named in v0.4.1 are fixed here, and that note needs two corrections.** Its heading said "both 0.4.2" and its body said "fixed together in 0.5.0" — one of those was always wrong, and 0.4.2 is the right one. And "Both are described in the README and the spec" is no longer true: fixing them deleted the paragraph that described them. The v0.4.1 note is left as written; this is the correction.

There is now one predicate per signal, used by both, and the capability report is derived from what was actually read.

- **A number that is not a token count no longer becomes one.** A data point's value was carried through an out-of-range float-to-integer conversion, which Go leaves to the machine: the same export read as `input: 9223372036854775807` on arm64 and `input: -9223372036854775808` on amd64. Negative values, `NaN` and infinity were all assimilated too. None of them reaches a profile now, and the reason names the point — in one of two clauses, because they are two different defects. Which of the two you get turns on how the leaf *read*, not on how large the number is. A leaf that *decoded as a finite number* whose rounded value is negative or 2⁶³ or beyond *is not a count* and is refused. A leaf that never decoded as a finite number at all — `NaN`, infinity, or a literal too big for its own reader — says nothing, so the next leaf is read; only when neither leaf yields a number is the point reported as carrying no readable value.
