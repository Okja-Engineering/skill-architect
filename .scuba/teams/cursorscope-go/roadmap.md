## A. Thesis

**Attribution is the prize; tokens are four different numbers wearing one name.** `skill-architect` has four profiler adapters. Three return `skill_activation: unknown` unconditionally (**Repository fact** — `claude_code.go:104`, `codex.go:74`, `devin.go:68`). The Cursor adapter is in a worse state than `unknown`: given an export containing `cursor.skill.activated`, `extractCursorSkillActivation` (`cursor.go:259-273`) returns **`present`** — but it reads `skill_name` / `trigger`, which are not the Wire Reference's `cursor.skill.name` / `cursor.skill.trigger`, so against a real export it emits a `present` activation with an **empty skill name**, and the repo's own test pins the defect (`profiler_test.go:560,605,644-652`, including `"trigger":"keyword"`, a value absent from Cursor's enum). All four adapters return `attribution: unknown` (**Repository fact**). Net: the profiler cannot say which skill did anything, and for Cursor it says so *confidently* — the exact failure this repo exists to prevent, and exactly the signal F04's paired comparison needs.

Cursor's free, local lifecycle hooks can supply attribution: session/turn/tool structure keyed by `conversation_id` → `generation_id` → `tool_use_id`, plus a skill name **inferred** from `beforeReadFile` on a `SKILL.md` path (inference, not an activation event — **Local hypothesis**, gated by spike SP1). That is the epic. Tokens are a separate, weaker story the research settled: hooks give **estimates** (`chars/4`, **−6.6%…+15.0%** measured vs `o200k_base` on markdown but *structurally* undercounting billed input, which is the cumulative conversation re-sent each turn); `afterMCPExecution.result_json` gives an MCP server's **self-report**; `preCompact.context_tokens` gives **one Cursor-reported number**, only on compaction; and genuinely billed tokens come only from **outside the hook surface** — `POST /teams/filtered-usage-events`, whose per-request `tokenUsage` joins the hooks' own `conversationId` (Team plan), or Enterprise OTel `cursor.api.request`. Four honesty levels. The profile must say which one it used, and the comparison engine must refuse to difference one against another.

### B.4 Design decisions closing register conflicts and contract gaps

- **D1 — Schema version.** All contract changes are additive, so the wire string stays `skill-architect/profile/v1` (`profiler-spec.md:161` bumps the suffix for *versions*; `:200` validates the exact string). The **spec document** is revised to **v1.1** with a changelog. Old profiles must still unmarshal — and, because **every field SC adds is `omitempty` and declared after the existing fields** (the new `Profile.ContextWindow` being a *pointer*, so `omitempty` actually applies to it), a pre-v1.1 golden also re-marshals **byte-identically**. SC proves it against a golden whose provenance is pinned, not hand-authored.
- **D2 — `present` redefined.** `MetricPresent`'s comment "value captured from telemetry" (`types.go:12`, `profiler-spec.md:19,33`) is false once `estimated` exists. SC rewrites it: *a value is available; `Source` names its provenance.* The rule "`Reason` empty when present" stays; provenance rides on `Source`, not prose.
- **D3 — Honesty classes: total, and fail-closed.** Every `MetricSource` constant maps to exactly one class: `measured_billed` (`server_api`) · `harness_reported` (`otel`, `otel_aggregate`, `hooks`, `session_data`, `sqlite`) · `self_reported` (`mcp_reported`) · `estimated` (`estimated`) · **`none` — both `SourceNone` (`types.go:46`) and the empty string, which is the zero value the six `Unknown*Result` constructors really leave (`types.go:196,216,231,246,261`); a metric that is not `present` has no honesty class, and a `present` result carrying either spelling is a contract violation the test catches.** The wire field is a free `string` (`types.go:23`), so the mapping is **fail-closed**: any *other* value outside the nine maps to class **`unrecognized`**, and `compare` refuses it, naming the offending string. `compare` refuses every cross-class comparison and names both classes. This is what makes an estimate un-differenceable against a billed number, and it repairs `compareTokens` dropping the baseline's source (`compare.go:115`).
- **D4 — `cursor_*_total` (R-CS-16) vs `skill_architect.skill.*` (R-RL-13).** R-RL-13 wins; **R-CS-16 dropped.** Emitting `cursor_*` from a tool that is not Cursor is precisely the invented-telemetry failure R-SA-14 forbids.

Each is derived here, once, under a caveat the spec doc and S8b's doc state verbatim — never silently:
  1. **Timestamps → we stamp them.** The ten base fields (ledger §A5.1:113) contain no timestamp and no payload row at :117-137 has one. S1a's binary writes **`received_at`** (RFC 3339 UTC) into the spool envelope, *outside* the `hook` object so it cannot be mistaken for Cursor's. `TimingData`, `ToolCallEntry.Timestamp` and `ActivationEntry.Timestamp` all derive from it and `TimingResult.Source` stays `hooks`, **with the caveat: wall-clock at hook receipt, not model time — it includes hook-process scheduling latency and excludes everything before the first hook fires.** `sessionEnd.duration_ms` (:118) is Cursor-reported and is used as a **test-time cross-check only**, never as a second provenance inside one result.
  2. **Tool-call outcome → `postToolUse` / `postToolUseFailure`, never `afterShellExecution`,** whose four documented fields (:124) contain no success signal. `postToolUse` → `success`; `postToolUseFailure` with `is_interrupt: true` → `aborted`; otherwise → `failure` (:122). A `preToolUse` with no terminal event → `aborted`, which is **rate-neutral** because `success_rate` excludes aborted from its denominator. No fourth value is invented. **`Status` is therefore always set on the hooks path** — which is what gives `success_rate` one definition across encodings.
  3. **Identifier kinds → one per field.** `ID` and `ParentID` hold **tool-call ids only**. The wire spelling differs by event: `tool_use_id` on `preToolUse`/`postToolUse`/`postToolUseFailure` (:120,121,122), **`tool_call_id` on `subagentStart`** (:131) — that one is the parent tool call and feeds `ParentID`. **`parent_conversation_id` (:131) is a conversation id and is barred from `ParentID`;** it is a reader-side join key only.
  4. **Attribution join → two forms, SP1 decides which.** `beforeReadFile` carries no `tool_use_id` (:127). **Form A:** if the same `(conversation_id, generation_id)` window holds a `preToolUse`/`postToolUse` whose `tool_input.file_path` matches `SKILL_PATH_RE`, `Attribution.Target` = that `tool_use_id`. **Form B:** otherwise `Target` = the output identifier `file://<workspace-relative path>`, generation-scoped. Both are permitted by the shipped contract — "tool call ID **or output identifier**" (`types.go:114`, `profiler-spec.md:154`) — which SC therefore must **not** narrow.
- **D12 — One result, one source; two quantities, two metrics.** A `TokenResult` has exactly one `Source` (`types.go:23`; spec `:36` "`Source` is always populated when `State == present`"), so four honesty labels cannot ride one `TokenCounts`, and S5/S6/S9 each writing it in turn is a silent overwrite. Two changes: **(a)** context-window occupancy is not token flow — `preCompact`'s three fields leave `TokenCounts` for a new **`context_window`** metric with its own `ContextResult` and its own `hooks` source; **(b)** `tokens` carries the **single best-honesty flow source**, chosen by S5's `selectTokenSource` over the total order `server_api` > `otel` > `mcp_reported` > `estimated`. Lower-ranked candidates are **discarded, not merged**, and S6/S9 register candidates rather than assigning `Profile.Tokens`. **`hooks` is not a token-flow label at all** — no hook event reports input/output/cache flow for a model call (ledger Q1:300) — so the only hook-derived flow number is the estimate. A `present` token result requires its chosen source to supply both `Input` and `Output`, else `unknown`-with-reason.
- **D13 — The comparison report versions independently of the profile.** `ComparisonSchema = "skill-architect/comparison/v1"` (`compare.go:11`) is a real wire string D1 never covered, and SC changes both `MetricComparison` and the tool-call maps. Rule: the same additive discipline as D1 — new fields `omitempty` and declared last, new map keys only added — so the string **stays** `v1`. The existing `Source` field keeps its meaning ("the candidate's source") and is retained alongside the new `BaselineSource`/`CandidateSource`, so no reader breaks. SC proves it with a pinned pre-change golden report.
