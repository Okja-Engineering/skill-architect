## Goal
Hooks become a first-class source alongside the OTel export file, and `experiment plan` / `experiment run` can drive a hook-sourced capture, closing the loop back to F04.

## Definition of done
1. `Probe()` reports hooks **and** OTel for the same metric via `Capability.Available map[MetricName][]MetricSource`, while `Capabilities` names the single source it will actually use. **This was proven impossible before the contract slice:** `Capabilities` is `map[MetricName]MetricSource` (`types.go:54`), so a second assignment silently overwrote the first and "reports hooks and OTel independently" was unassertable. S7 does not own `types.go`; SC-a does.
2. `Condition` / `ExperimentStep` carry a `HookSpool` path (R-SA-15).
3. **The two experiment wire strings survive it, and the proof is inherited rather than rewritten (V4-#6).** `ExperimentSchema` (`experiment.go:14`) and `ExperimentPlanSchema` (`experiment.go:17`) are strictly validated (`experiment.go:98-99,237-238` reject any other value), so DoD 2 is a change to two live wire formats — the case D1/D13's additive rule never covered until SC-a item 16. `HookSpool` is therefore **`omitempty` and declared last** on both structs, and **SC-b's** pinned goldens `testdata/golden/experiment-v1-pre11.json` and `experiment-plan-v1-pre11.json` must still re-marshal **byte-identically**. That check lives in SC-b's `compare_contract_test.go` and runs on every PR, so this slice inherits it: declare the field wrongly and CI goes red in a file this slice does not own and does not need to edit. Neither schema string moves.
4. `profiler compare` on two hook-sourced profiles returns `comparable: true` for `tool_calls` **and** `skill_activation`, with **both** sides' sources present in the report (SC-b's `BaselineSource`/`CandidateSource`).
5. **Cross-encoding comparison is asserted, not assumed, inside the gate SC-b defines *and over the same call set* (C3-#2, V4-#8, V5-#4).** Round 2 claimed encoding-invariance held "even if one side is later re-captured from the OTel aggregate path" while S1b left `Status` empty on the hooks side and S0 carried it through on the OTel side — the two sides then had different `success_rate` denominators and the claim was false. Three changes make it true and this DoD tests it rather than asserting it: **S1b now always sets `Status`** (D11), **S0's aggregate rows always carry `cursor.tool.status`**, and **SC-b defines `successes` exactly once** and gates the outcome figures on both sides carrying `Status` (SC-b items 13, 14).
   **The claim, with the scope condition round 4 omitted:** a hooks-sourced profile and an OTel-aggregate profile of the same session — both `Status`-bearing, therefore both inside the gate — compare to **zero delta** on `count`, `successes`, `failures`, `aborted` and `success_rate` **provided the two sides cover the same call set.** That holds when the OTel side is captured **without `--session`** over an export containing only that conversation, or **with `--session`** over a **provably single-conversation** export (S0 DoD 3). It does **not** hold on a multi-conversation export, because `cursor.tool.calls` carries no conversation id — and there S0 emits `tool_calls: unknown` under SC-a item 8's eligibility rule rather than an export-wide row set wearing the session's name. **Both halves are asserted here**, since this is the only slice where two real adapters meet. The out-of-gate case (a pre-v1.1 `Status`-less profile) is SC-b's to prove, not this slice's.
6. **The two token call sites collapse to one (V5-#3, D12).** Unifying the adapter means the OTel branch (S0's call site in `cursor.go`) and the hook branch (S1b's call site at the end of `enrich()`) become one capture path with **exactly one** `ApplyTokenSelection` call over one accumulator. This is the slice where the single-writer invariant stops being "one assignment per branch" and becomes "one assignment, full stop" — and it is asserted, not assumed.

## Test approach
`profiler/unify_test.go` (new, this slice's own file):
- a probe test asserting two distinct sources are reported for one metric, and that `Capabilities` still names exactly one;
- a compare test over two hook-sourced fixtures asserting `comparable: true` for both metrics and both source labels in the output;
- **a cross-adapter mixed-encoding compare (DoD 5, in-gate, same call set):** one profile captured through S1b's hook path (per-call rows, `Status` set from `postToolUse`/`postToolUseFailure`) against one through S0's OTel path (aggregate `Count` rows, `Status` from `cursor.tool.status`) **over a single-conversation export** for the same session, asserting zero delta on all five tool-call figures — with the fixture deliberately **heterogeneous** (mixed success / failure / aborted), because a homogeneous one cannot fail — and asserting that the four outcome keys are **present**, i.e. that both real adapters land inside SC-b's gate rather than silently having their figures withheld;
- **the out-of-scope half of DoD 5 (new at round 5):** the same hook-sourced profile against an OTel capture taken with `--session` over a **multi-conversation** export, asserting `tool_calls` is `unknown` with `UnscopedAggregateReason("cursor.tool.calls", …)` and that `compare` reports `comparable:false` naming it — never a zero delta computed over two different call sets;
- an `experiment run` test driving a hook-spool condition end to end, plus a re-marshal assertion on a plan produced **after** `HookSpool` is added, showing the field is absent from the JSON when unset (DoD 3's local half; SC-b's goldens carry the rest);
- an assertion that a retracted metric yields `unknown`-with-reason, never a silent zero;
- an assertion that `tokens` and `context_window` are compared as **separate** metrics with separate sources, through **SC-b's `compareContextWindow`** (SC-b item 10) — round 3 asserted this against a `CompareProfiles` that had five comparators and no `context_window` at all (**`compare.go:90-94`**), so the claim had no code to bind to (V4-#4; line range corrected at round 5, V5-#8). SC-b ships the comparator; this slice proves it end to end, so a `preCompact`-derived occupancy number can never be differenced against a token-flow number;
- **an AST assertion for DoD 6:** exactly one `ApplyTokenSelection` call exists in the unified Cursor path, and no file in the Cursor-path set assigns `Profile.Tokens`.
§G14 flags that `CompareProfiles` has been read but never exercised against a hook-sourced profile — these tests are what convert that from assumption to fact. If they fail, S7 grows and R-SA-06 becomes a real constraint rather than a formality.
