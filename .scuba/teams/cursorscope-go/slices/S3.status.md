## Definition of done
1. `classifyInvocation` returns one of exactly five categories — `mcp | cli | skill | subagent | tool` — with a name and detail across cursorscope's transcribed table. The five values are **External evidence**, read from the literal `category:` assignments in `src/attribution.js:174,183,193,226,234,242`, not from prose. Its inputs are all supplied: `mcp_server_name` / `tool_name` (`beforeMCPExecution`/`afterMCPExecution`, ledger §A5.1:125,126), `command` (`before`/`afterShellExecution`, :123,124), `subagent_type` (`subagentStart`, :131), `tool_name`/`tool_input` (`preToolUse`, :120).
2. A `Profile` built from **SP1's real fixture** reports `skill_activation: present` with a **non-empty** `SkillName` — from `beforeReadFile.file_path` through `skillNameFromPath` (ledger §A5.1:127,143) — `Source: "hooks"`, and `Trigger: "inferred_file_read"`. `ActivationEntry.Timestamp` comes from the spool envelope's `received_at`, **not** from Cursor: no hook event carries a timestamp (§A5.1:113), and D11's caveat applies verbatim.
3. **`attribution: present`, joined by the form SP1 confirms (V3-#5, D11).** `beforeReadFile` carries `file_path`, `content` and `attachments` and **no `tool_use_id`** (ledger §A5.1:127), so a tool-call-id target is not derivable from the inferring event alone. Two forms, in priority order, both permitted by the shipped contract's "tool call ID **or output identifier**" (`types.go:114`, `profiler-spec.md:154`):
   - **Form A (strong).** If the same `(conversation_id, generation_id)` window contains a `preToolUse`/`postToolUse` whose `tool_input.file_path` matches `SKILL_PATH_RE`, `Attribution.Target` = that event's **`tool_use_id`**, and it resolves to a `ToolCallEntry.ID` in the same profile. Both ids are base-field-supplied (§A5.1:113,120,121).
   - **Form B (fallback).** Otherwise `Target` = the output identifier **`file://<workspace-relative file_path>`** (redacted by S4), and the activation is scoped to the generation in whose window the `beforeReadFile` was received — `generation_id` is a base field on `beforeReadFile`, so the window join is supplied (§A5.1:113).
   The slice implements Form A when available and Form B otherwise, and **records in the profile which form produced each target** via the `Trigger` and the target's scheme prefix. Round 1 said "mapping at least one `tool_use_id` to that skill", which no hook event supplies; round 2 asserted a `ToolCallEntry.ID` resolution the inferring event cannot produce. This is R-SA-07, the epic's primary success condition, in the form the surface actually permits.
4. The `Trigger` value comes from the **hook-inferred** vocabulary only — `inferred_file_read | inferred_shell_command | inferred_subagent` (**D6**, a Design decision of this epic), which is disjoint from Cursor's first-party enum `agent_read | manually_attached | skill_name_in_prompt` (**Specification**, ledger §A5.2:169). SC defines both sets; this slice may emit only the `inferred_*` one.

- a negative test that no `inferred_*` value can be written where a first-party trigger belongs and vice versa (D6 is enforceable, not just documented).
