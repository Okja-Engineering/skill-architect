## Goal
One slice owns `profiler/compare.go` and the three comparison/experiment goldens, and gives the contract the *code that enforces its comparison rules*: a `context_window` comparator, both sides' sources on every comparator, `successes` defined exactly once, the comparability gate, and the wiring that makes SC-a's validator load-bearing.

**Created at round 5 by splitting `SC` on the seam §H2 named** (V5-#15). SC-a ships the channels and two pure functions; nothing in it touches the comparison wire format. This slice is the other half, and it is the one that changes a **shipped, strictly-validated** wire string's contents — which is why its goldens live here.

## Definition of done
10. **`compare.go` gains a `context_window` comparator (V4-#4).** `CompareProfiles` (`compare.go:90-94`) has exactly five comparators — `tokens`, `tool_calls`, `timing`, `skill_activation`, `attribution` — and no `context_window`, so S7's "compared as separate metrics" had no code to bind to and D12's separation stopped at the type level. This slice adds `compareContextWindow` and `report.Metrics["context_window"]`, carrying both sides' sources and refusing a cross-class comparison like every other comparator. Adding a map key is exactly what D13's rule permits, so `ComparisonSchema` stays `v1`.
    - **The nil case, stated (V5-#12).** `Profile.ContextWindow` is a **pointer** (SC-a item 5) and is nil on every pre-v1.1 profile, on every hooks-only capture of a session that never compacted, and on all four shipped adapters. So `compareContextWindow` takes `*ContextResult` on both sides and: **nil on either side → `Comparable:false` with `Reason:"context_window not captured in <baseline|candidate>"`; nil on both → `Comparable:false` naming both.** Never a zero-valued `ContextData` standing in for "not captured" (R-SA-02), and never a nil dereference — the failure mode a value-typed comparator would have shipped.
11. Every comparator carries **both** sides' sources (`BaselineSource`, `CandidateSource`) and refuses a cross-class comparison, naming both classes. Today `compareTokens` (`compare.go:106-126`) gates only on `State == present` and reports the *candidate*'s source (`compare.go:115`), so an `estimated` baseline against a `server_api` candidate yields `comparable:true, source:"server_api"` and the estimate's honesty label vanishes. The existing `Source` field is **retained** and keeps meaning "the candidate's source", so no consumer breaks (D13). **Both new fields are `omitempty` and declared last on `MetricComparison`, per SC-a item 17** — which round 4 scoped to items 1–9 and so left these two uncovered (V5-#11).
12w. **SC-a's `ValidateProfile` is wired here, which is what makes it non-decorative.** `CompareProfiles` runs it on both profiles and appends each violation to `ComparisonReport.Notes` (an existing field, **`compare.go:40`**, appended at `:81,84,87` — additive, no schema change). **This is the slice where V5-#5 would have detonated:** with round 4's validator rule (c), every pre-v1.1 row's `Status: ""` was a violation, so the first legacy comparison after this wiring would have flooded `Notes`. SC-a's rule (c) now rejects a *wrong* value, not an *absent* one, and this slice's test pins that on a real legacy fixture.
13. **Tool-call comparison is encoding-invariant, with `successes` defined exactly once (V3-#1, C3-#2).** `countToolCalls` (`compare.go:148-155`) is `len(calls)` and `successRate` (`:158-163`) divides by all rows — so once S0 emits aggregate `Count` rows, the same session compares nonzero against itself. **This is why S0 depends on this slice** (see § Next). Round 2 replaced that with **two** definitions of `successes` whose numbers disagree; round 3 replaced both with **one**:
    - a row's **outcome** is `Status` when set, else derived from `Success` (`true` → `success`, `false` → `failure`) — this is the only place the legacy field is consulted;
    - `count` = Σ `Count` (an absent or zero `Count` counts as 1); `successes` / `failures` / `aborted` = Σ `Count` over rows of that outcome;
    - `success_rate` = `successes / (successes + failures)`, and `0` when that denominator is 0 — an aborted call is neither a tool success nor a tool failure.
    **The 34 existing tests do not move as a consequence, not as a special case:** a pre-v1.1 profile has no `aborted` outcome, so `successes + failures == count` and the rate is arithmetically identical to today's.
14. **The comparability gate — what the invariant actually guarantees (V4-#8).** Round 3 claimed "zero delta **regardless of row encoding**", which its own next bullet falsified: a `Status`-less encoding of the same session yields `success_rate` 0.50 where a `Status`-bearing one yields 0.75, because the legacy fallback reads a `false` `Success` as `failure` while the hooks path calls the same call `aborted`. That is not a bug in either rule; it is two encodings that carry different information, and the contract must say so rather than promise a delta it cannot deliver. The gate:
    - `count` compares **always**, across every encoding — it needs no outcome information;
    - the four outcome figures (`successes`, `failures`, `aborted`, `success_rate`) are emitted **only when both sides carry a non-empty `Status` on every row**. If either side has a single row without `Status`, those four keys are **absent** from `baseline`, `candidate` and `delta`, and `MetricComparison.Reason` reads *"outcome figures not comparable: <baseline|candidate> encodes tool calls without Status"* while `Comparable` stays `true` for `count`. (`MetricComparison` carries one `Comparable` flag for the whole metric, **`compare.go:23-30`**, and the tool-call figures ride in three `map[string]any` values — so "the `success_rate` row is not comparable" is expressed by omitting the key and naming the reason, not by a second flag. Stated here so no reader expects a per-figure boolean that the shipped shape has no room for.)
    - **`Status: ""` is a legal encoding, not a violation.** This gate is the *only* place the contract reacts to it; SC-a's validator does not flag it (V5-#5). One rule, one reaction.
    - **The invariant, restated to what the gate guarantees:** *two profiles of one session yield zero delta on `count` in every encoding, and zero delta on `successes`, `failures`, `aborted` and `success_rate` **whenever both sides carry `Status` on every row** — per-call and aggregate-`Count` encodings included.* S1b always sets `Status` (D11.2) and S0 carries `cursor.tool.status` through, so both v1.1 producers satisfy the gate; a pre-v1.1 profile does not, and now says so instead of differencing 0.75 against 0.50.
    - **What the gate does *not* cover, said once so S7 does not over-claim (V5-#4):** it guarantees zero delta only when both sides cover **the same call set**. An OTel-aggregate profile captured with `--session` over a *multi-conversation* export does not — `cursor.tool.calls` carries no conversation id — which is why S0 emits `tool_calls: unknown` there rather than an export-wide row set wearing a session's name (SC-a item 8's eligibility rule).
16b. **The three remaining goldens (V4-#6; SC-a item 16 states the rule).** This slice pins `profiler/testdata/golden/comparison-v1-pre11.json`, `experiment-v1-pre11.json` and `experiment-plan-v1-pre11.json`, and proves byte-identical re-marshal on each. `comparison-` is the additivity proof for item 11's two new `MetricComparison` fields; the two experiment goldens exist because **S7 adds `HookSpool` inside both experiment structs**, and the golden then **fails in CI the moment S7 declares it wrongly**, so S7 inherits the guardrail without editing this slice's file. It edits **no** line of `experiment.go`.
19b. **`docs/profiler-spec.md` gains the comparison-side sections** — the outcome rule and **the comparability gate in the form item 14 states it** (items 13, 14), the `context_window` comparator and its nil case (item 10), both-sides sources (item 11), and D13's comparison-report rule extended to the two experiment schemas (item 16b). SC-a wrote the channel sections one wave earlier, in the same file, in different sections.

## Test approach
`profiler/compare_contract_test.go` (new, this slice's own file — SC-a's `contract_test.go` is not edited, so the two halves never collide):
- **Golden provenance pinned exactly as SC-a pins it (V3-#15):** each of the three goldens is generated **once** by marshalling a fully-populated value through the *merge-base* source (`git show <merge-base-sha>:profiler/compare.go`, `:profiler/experiment.go`) and committed verbatim; producing command and SHA in a header comment. All three then re-marshal byte-identically;
- `compareTokens(baseline: estimated, candidate: server_api)` → `comparable:false` with a reason naming both classes; `compareTokens(baseline: "wat", candidate: hooks)` → `comparable:false` naming the unrecognized string (fail-closed); `compareTokens(baseline: hooks, candidate: otel)` → `comparable:true` reporting **both** sources;
- **`compareContextWindow` (item 10):** two `present` `context_window` results compare with both sources reported; a `context_window` result and a `tokens` result occupy **different keys** in `report.Metrics` and no code path differences one against the other; **and the nil cases — nil baseline, nil candidate, nil both — each yield `comparable:false` with the naming reason and no panic** (V5-#12);
- **encoding invariance over heterogeneous fixtures (V3-#1, item 13).** The fixture is *deliberately mixed* — a 6-call session of 3 `success` / 1 `failure` / 2 `aborted`, in **both** `Status`-bearing encodings (six per-call rows; three aggregate rows carrying `Count` 3/1/2) — compared to **zero** delta on `count`, `successes`, `failures`, `aborted` and `success_rate`, with `success_rate` = 0.75 on both sides. A homogeneous fixture cannot catch the defect this rule exists to prevent, so it is not sufficient here;
- **the gate (item 14):** a third encoding of the same session with `Status` empty and `Success` set (the pre-v1.1 shape) compared against either `Status`-bearing encoding asserts `count` delta 0, the four outcome keys **absent** from all three maps, and the reason string naming the offending side — the assertion that replaces round 3's false "regardless of row encoding" claim;
- **the validator wiring (item 12w):** a `CompareProfiles` run over a violating profile carries the violation into `ComparisonReport.Notes`; **and a `CompareProfiles` run over two pre-v1.1 `Status`-less profiles produces an empty `Notes`** — the regression V5-#5 predicted, pinned.

All **34 existing Go tests stay green** — no field is removed, no default changes, `ValidateProfile`'s only wired call appends to an existing `omitempty` slice, and item 13's arithmetic is identical to today's on any profile with no `aborted` outcome.

**Why S0 depends on this slice and not only on SC-a (a round-5 deviation, stated rather than buried).** The round-5 instruction recomputed S0 → SC-a. That is right for every channel S0 needs, but it is one edge short: **S0 is the slice that starts emitting `Count`-bearing aggregate rows**, and on `main` `countToolCalls` is `len(calls)` (`compare.go:148-155`). If S0 merged before this slice, `profiler compare` would report `count` 3 where the session had 6 and `success_rate` 1.0 where it was 0.5 — the exact HIGH (V2-#1) item 13 exists to fix, shipped by an MVE slice into the merge window between the two. S0's own DoD 4 asserts the consequence ("these `Count`-bearing rows compare to zero delta against S1b's per-call rows"), so the dependency is genuine and declared, not invented. The cost is one wave of depth for S0; the alternative is an MVE that knowingly ships a wrong comparison. **The primary MVE therefore contains both halves — ten PRs, not nine.**

**Do not fold this back into SC-a.** The two halves have disjoint files, disjoint test files and disjoint reviewers' concerns: SC-a is "does the type carry it", SC-b is "does the comparison say the truth about it". Recombining them reproduces the 19-item PR §H2 flagged.
