# S5 — Token honesty: one label per result, chosen by rank

- **Stage:** parked — **gated on User Question 3** (Fork vi)
- **Owner:** unassigned
- **Branch:** none (target: `epic/skill-scope`)
- **Depends on:** **SC, S1b**
- **Blocks:** S7, S9, S10

## Goal
Produce every hook-derived token number under a label that names its honesty, so no reader — and no comparison — can mistake any of them for billed tokens. SC ships the *channels*; this slice ships the *producers* **and the selection rule that keeps one result to one source**.

**The old dep on S3 was phantom** and is removed: token extraction needs no attribution, and parking S5 behind the slice most likely to collapse (S3, gated on SP1) was invented sequencing.

**Retitled at round 3.** "Four sources, four labels" was unimplementable as written: a `TokenResult` has exactly **one** `Source` (`types.go:23`; `profiler-spec.md:36` "`Source` is always populated when `State == present`"), so four labels cannot ride one `TokenCounts`, and S9 filling the same struct later was a silent overwrite. The repair is **D12**, in two parts.

## Definition of done

**Part 1 — the two quantities are separated (D12).** Context-window occupancy is not token flow, and conflating them is what created the four-labels problem:

| Metric | Carrier | Supplier | Label | Class (D3) |
|---|---|---|---|---|
| `context_window` | SC's `ContextResult` (`ContextTokens`, `ContextWindowSize`, `ContextUsagePercent`) | `preCompact` — all three fields, ledger §A5.1:136 | `hooks` | harness_reported |
| `tokens` | `TokenCounts` (unchanged from v1) | one flow source, selected below | that source's label | that source's class |

**Part 2 — `tokens` carries exactly one source, chosen by a named total order.** `selectTokenSource` is defined in this slice, is the *only* writer of `Profile.Tokens`, and ranks candidates best-honesty-first: **`server_api` (S9) > `otel` (S6) > `mcp_reported` > `estimated`**. The highest-ranked candidate that produced a value wins; **lower-ranked candidates are discarded, not merged** — no field of `TokenCounts` is ever filled from a source other than the one named in `TokenResult.Source`. S9 and S6 register candidates through this function rather than assigning `Profile.Tokens` themselves, which is what makes "no silent overwrite" mechanical instead of a convention.

| Flow candidate | Supplier | Label | Class |
|---|---|---|---|
| `chars/4` over hook payloads — `beforeSubmitPrompt.prompt`, `postToolUse.tool_output`, `afterShellExecution.output`, `beforeReadFile.content`, `afterMCPExecution.result_json`, `afterAgentResponse.text`, `afterAgentThought.text` (ledger Q1:300) | hooks, estimated | `estimated` | estimated |
| `afterMCPExecution.result_json` → `usage`/`token_usage`/`tokens` (**External evidence** — cursorscope's probe, ledger §A5.1:142; not a documented Cursor field) | MCP server self-report | `mcp_reported` | self_reported |
| Enterprise OTel `cursor.api.request.*_tokens` | **S6** | `otel` | harness_reported |
| Admin API `tokenUsage` | **S9** | `server_api` | measured_billed |

3. **`hooks` is not a token-flow label, and this slice must not emit one.** No hook event reports input/output/cache-read/cache-creation for a model call — ledger Q1:300 says so in those words, and the payload table §A5.1:117-137 bears it out. The only hook-derived flow number is the `chars/4` estimate, and it is labelled `estimated`. `hooks` appears on `context_window` only.
4. **A `present` token result requires the chosen source to supply both `Input` and `Output`.** Otherwise the metric is `unknown` with a reason naming the source and the missing field — never a `present` result with a zero standing in for "not supplied" (R-SA-02). `CacheRead`/`CacheCreation`/`Reasoning` are `omitempty` and simply absent when the source does not carry them.
5. No value produced by an `estimate*` function ever serializes with any other source (S8a's guardrail 2 enforces it). `docs/profiler-spec.md` records the structural undercount, that `preCompact` fires **only** on compaction (ledger §A5.1:141), and the selection order above.

## Test approach
`profiler/tokens_test.go` (new, this slice's own file):
- one fixture per candidate asserting its exact `Source` string **and** the honesty class SC maps it to;
- a **selection** table — the heart of the slice: a spool yielding both an `estimated` and an `mcp_reported` candidate produces `Source: "mcp_reported"` and a `TokenCounts` whose fields all come from the MCP report; adding a `server_api` candidate flips it to `server_api` and **changes every field**; asserting in each case that no field retains a value from a discarded candidate;
- a `preCompact` fixture asserting `context_window` is `present` with `Source: "hooks"` and all three fields populated, **and that `Profile.Tokens` is unaffected by it** — the assertion that proves D12's separation actually holds;
- a no-compaction fixture asserting `context_window` is **absent** (nil pointer, omitted from JSON) rather than a zero-valued `present`;
- a fixture whose only candidate supplies `Input` but not `Output`, asserting `tokens: unknown` with the reason naming both (DoD 4);
- a negative test that `compare` **refuses** `estimated` vs `server_api` (SC's cross-class rule), so an estimate can never be silently differenced against a billed number — the failure `compareTokens` allows today, where the baseline's source is dropped entirely (`compare.go:115`).
