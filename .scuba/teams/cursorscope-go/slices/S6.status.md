# S6 — Per-request tokens + conversation scoping (Enterprise OTel)

- **Stage:** parked — gated on User Question 2 (Cursor plan tier)
- **Owner:** unassigned
- **Branch:** none (target: `epic/skill-scope`)
- **Depends on:** **SC-a** (the `otel_aggregate` constant, `TokenCandidate`, `SessionEligible` and `UnscopedAggregateReason`), **S0** (creates `cursor_wirekeys.go`, owns the `extractCursor*` helpers this slice extends, computes the export's conversation set, and owns the OTel branch's single `ApplyTokenSelection` call site)
- **Blocks:** none

## Goal
Read `cursor.api.request.{input,output,cache_read,cache_creation}_tokens` per request and scope a capture by `cursor.conversation.id`, instead of throwing those fields away and summing a session-blind aggregate metric. All five keys are **Specification** (ledger §A5.2:152 for the join key, :166 for the four token attributes).

## Definition of done
1. Given an export containing two conversations, `capture --session <cursor.conversation.id>` returns tokens for **only** that conversation, and the scoped totals differ from the unscoped ones. This is supplied: `cursor.api.request` is a **log** event, and `cursor.conversation.id` is a documented log join key (ledger §A5.2:152). It is also the record S0's `exportConversations` set is derived from (S0 DoD 3), so this slice makes that set richer rather than introducing a second reader.
2. **The aggregate fallback is unscopable, and the DoD says what that costs (V3-#8).** `cursor.token.usage` is a metric whose only attributes are `cursor.token.type`, `cursor.model.name` (opt), `cursor.api.status` (opt) and `cursor.api.billable` (opt) — **there is no conversation id on it** (ledger §A5.2:158). So the fallback is **export-scoped, never session-scoped by its own attributes**, and the cases split under SC-a item 8's one eligibility predicate:
   - **no `--session`** → the aggregate candidate is eligible and, absent a per-request candidate, wins: `Source: "otel_aggregate"`, and the spec doc records that the number covers the whole export;
   - **`--session <id>` given, no per-request events, export not provably single-conversation** → the aggregate candidate is **ineligible** and `tokens` is `unknown` with `UnscopedAggregateReason("cursor.token.usage", id)`. **Not** a silently unscoped sum wearing a session's name, which is the R-SA-02 failure this epic exists to prevent;
   - **`--session <id>` given and the export is provably single-conversation** (S0 DoD 3's detection: the distinct `cursor.conversation.id` set over the export's log records is exactly `{id}`) → the aggregate is admitted, carrying `CaveatExportScopedAggregate`. **This slice's aggregate-only fixture has no log records at all, so the set is empty, single-conversation is not established, and the fixture asserts `unknown`** — the escape does not weaken the assertion round 3 could not make (V5-#4).
   `cursor.model.name` is the only further scoping the metric permits, and this slice does not use it.
3. **The new `cursor.*` literals live in `profiler/cursor_wirekeys.go`** (D5). This slice therefore **owns that file jointly with S0**, which creates it a wave earlier. Round 2 caught that S6's DoD requires new wire keys while its Files omitted the only file allowed to hold them, which made the slice unbuildable as scoped under S8a's guardrail 4.
4. **Two candidates, two labels, and the label matches the metric that produced it — registered, never assigned (V4-#1, C4-#2, V5-#3, D12).** This slice **registers candidates and calls nothing that assigns**: it `Add`s to the `*TokenCandidates` accumulator S0's OTel branch already threads, and **inherits S0's single `ApplyTokenSelection` call site rather than adding a second**:
   - per-request `cursor.api.request.*_tokens` → `TokenCandidate{Source: "otel", SessionScoped: true}`;
   - the `cursor.token.usage` fallback → `TokenCandidate{Source: "otel_aggregate", SessionScoped: false, SingleConversation: <S0's boolean>}` — **the same label S0 registers for the same metric**, because it is the same export-wide number read by the same rule. Round 3's DoD 2 said the fallback labels the result `otel_aggregate` while its DoD 4 said the slice "registers an `otel` candidate", so one slice named one number two ways and neither label was ranked (C4-#2).
   SC-a's total order ranks `otel` above `otel_aggregate` above `mcp_reported` above `estimated`, so the mixed case resolves without this slice deciding anything: **per-request wins, the aggregate is discarded rather than added to it, and nothing double-counts.**
5. **Degrades, never fails hard (R-SA-13).** An export with no `cursor.api.request` events and no `cursor.token.usage` metric registers no candidate at all; `tokens` is `unknown` with SC-a's empty-list reason, every other metric is unaffected, and the command exits 0. The register assigned R-SA-13 to this slice; round 3's `## Requirements` did not carry it (V4-#14).

## Test approach

Fixtures spell `cursor.*` keys directly — the second place D5 allows is `*_test.go`.
